# Issue #295: AD_RESET の busy 境界の観測契約（測定手順の固定）

親 #25。前提 PR: #403（`ad_reset_idle` guest 実装）、#404（idle 実コア観測ドライバ）は main に統合済み。関連: [ad-reset-diagnostic.md](ad-reset-diagnostic.md)（#294、idle と play の device 層診断）、[ad-reset-contract.md](ad-reset-contract.md)（#292、ABI 台帳）、[ad-reset-fixture.md](ad-reset-fixture.md)（#293、合成 fixture）。

**状態: 契約のみ。実コア測定は未実施。`BLOCKED_ABI`、`release_eligible=false`、`DEV_CALLABLE` 不可。System Card 互換の VERIFIED とは主張しない。**

本書の目的は、実測の前に測定手順と判定基準を固定することである。reset 後のフラグ、RAM、IRQ、転送の中断結果などの期待値は、本書では決め打ちしない。期待値を含む判定は、測定ログを取得した後に別文書で行う。

## 2. 区分別の成立確認手順

本節は「busy が立つと想定する操作」ではなく、各測定区分の試行を成立させ、確認するための手順である。成立の判定は §3 の観測で行う。

### 2.1 PLAY_ACTIVE（再生中）の手順

1. ハーネスは device 層の `Adpcm::Write` だけで ADPCM を設定する（CPU 命令経由の MMIO 書込みは使わない）。
   - ADDRESS と LENGTH は、本書で固定した値（`ADDRESS = $1234`、`LENGTH = $0400`）を書く。
   - CONTROL は `$20`（bit5 = 1、bit7 = 0）を書く。#294 の `neg-reset-playing` で再生を開始したのと同じ経路である。
2. `RunToVBlank` で 1 フレームずつ進め、§3.2 の T_b で再生中を観測する。
3. 観測できるまで最大 60 フレームまで待つ（§6）。観測できない試行は `UNOBSERVED_BUSY` とする。

### 2.2 TRANSFER_BUSY（転送 busy）の手順

本区分は現時点で **BLOCKED** である。成立の条件と BLOCKED の理由は §3.4 に記す。BLOCKED の間は、この区分の試行を実行しない。

## 3. 観測点と測定区分

### 3.0 ステータスレジスタ（`$180C`）のビットの意味（固定版ソースの読取り）

読取りのみ（`src/adpcm_inline.h`、`src/adpcm.cpp`、いずれも固定版 `b49ae82a`）。

| ビット | 固定版ソースの定義 | 根拠（行） | 本契約での扱い |
| --- | --- | --- | --- |
| `$08` | `m_playing` | `adpcm_inline.h:84` | 再生中。ソースの意味として確定 |
| `$01` | `m_end_irq` | `adpcm_inline.h:85` | END IRQ 要求。ソースの意味として確定 |
| `$80` | `m_read_cycles > 0` | `adpcm_inline.h:86` | 「データポート読出しの待ち時間カウンタが 0 でない」。ソースでは busy という名前は使われていない。転送 busy を表すかどうかは **UNKNOWN** |
| `$04` | `m_write_cycles > 0` | `adpcm_inline.h:87` | 同上（書込み側）。DMA 経路でも設定される（`adpcm_inline.h:204`）。転送 busy を表すかどうかは **UNKNOWN** |

補足（ソースの事実）:

- `$0A` の読出しは `m_read_cycles` を設定し（`adpcm_inline.h:65`）、`$0A` の書込みは `m_write_cycles` を設定する（`adpcm_inline.h:102`）。
- 待ち時間は `ComputeLatency` により最大 36 の単位で、毎クロック減算される（`adpcm.cpp:215-234`、`adpcm_inline.h:140-172`）。つまり、`$0A` 経由の `$04` / `$80` は、フレームより短い時間幅で消える。
- `$0C` の読出し（`GetStatusRegisterSnapshot`）は副作用がない。`$0A` の読出しは副作用があるため、観測では呼ばない（#294 と同じ）。
- 旧版（#577 の初版）で `$04` / `$80` を busy ビットと記していたのは、#294 の文書の表現を引き継いだもので、ソースの名称ではない。本版で訂正する。

### 3.1 観測する状態

| 観測点 | 読む対象 | 経路 | 副作用 |
| --- | --- | --- | --- |
| S1: ステータス | ADPCM_STAT（`$180C`） | device 層の `Adpcm::Read`（ハーネス側） | なし |
| S2: 内部状態 | PLAYING、ADDRESS、READ/WRITE_ADDRESS、LENGTH、`m_read_cycles`、`m_write_cycles` | `Adpcm::GetState()` 等の読取り | なし |
| S3: 時刻 | 経過フレーム数、CPU ステップ数 | ハーネスのカウンタ | なし |

### 3.2 観測の時点

- T_b（区分の成立確認時）: S1 と S2 を同時に読む。
- T_r（reset 発行直前）: S1 と S2 を再び読む。
- 正例の条件は、区分ごとに §3.3 で定める。T_b と T_r の両方で条件を満たしたときだけ、その試行を正例の候補とする。

### 3.3 測定区分名

| 区分名 | 定義 | 正例の候補となる条件 |
| --- | --- | --- |
| PLAY_ACTIVE | 再生中であることを観測した試行 | T_b と T_r の両方で、S1 の `$08` が 1 かつ S2 の PLAYING が 1 |
| TRANSFER_BUSY | 転送処理が busy であることを観測した試行 | **BLOCKED**（§3.4）。現時点でこの区分の試行は存在しない |
| UNOBSERVED_BUSY | 対象の busy 成立を確認できなかった試行 | 正例にしない。証拠として使わない。件数だけを報告する |

- 試行は必ず上の 3 区分のいずれか 1 つに分類する。
- **PLAY_ACTIVE の PASS を TRANSFER_BUSY の PASS へ流用しない。** 再生中の reset の結果は、転送 busy 中の reset の結果としては扱わない。
- `UNOBSERVED_BUSY` の試行は、他の区分の正例にも負例にも含めない。

### 3.4 TRANSFER_BUSY が BLOCKED である条件

以下のいずれかが満たされない限り、TRANSFER_BUSY は BLOCKED とする。

1. **`$0A` 書込み経路（device 層）**: `$04` の待ち時間は 1 回の書込みにつき最大 36 単位で消える（§3.0）。本ハーネスはフレーム境界（`RunToVBlank`）でしか観測点を持たないため、T_b と T_r の両方で値が立っていることを、フレーム境界では保証できない。サブフレームの観測点を、CPU 実行の外側（ハーネス側）で定義し、その安全性を #173 の条件に照らして確認するまで BLOCKED とする。
2. **`$0B` の DMA 経路**: `$04` は DMA 経路でも立つ（`adpcm_inline.h:204`）。DMA 経路は SCSI コントローラの信号（`adpcm_inline.h:219-225`、`DataReady` など）に依存し、その設定は CD 側の操作である。#173 の B3（デバイス起点の書込み）と B6（CD 側 MMIO）に抵触するため、BLOCKED（§10 の B11）。
3. **`$80` の意味**: `m_read_cycles` は `$0A` の読出しで立つ。転送の意味を持つかは UNKNOWN であり、どの経路でも確定していない。

解除の条件（3 つすべて）:

- サブフレームの観測点（ハーネス側の停止点）を定義し、CPU 実行の強制停止が #173 の条件に抵触しないことを、独立レビューで確認する。
- `$04` / `$80` が転送 busy であることを、ソースまたは実測で確定する（UNKNOWN を解消する）。
- 独立レビューで、TRANSFER_BUSY の観測点と判定基準の固定を承認する。

## 4. reset 要求の発行方法（手順のみ）

1. T_r の時点（フレーム境界。区分名に関わらず同じ）で、ハーネスが `Adpcm::Write` を 1 回だけ呼ぶ。書込み先は CONTROL（`$180D`）、値は `$80`（bit7 = 1、bit5 = 0）とする。
2. reset 要求はハーネスからのみ発行する。CPU 命令による `$180D` への書込みは行わない（§10 の B9）。
3. reset の発行は 1 試行につき 1 回とする。再発行はしない。
4. 別系統として、bit5 を 1 のまま残す値（`$A0`）での要求を、区分 `arm-B` として別に測る。`arm-B` は正例の集計に入れない。

## 5. reset 前後で採取する範囲

採取は T_r（発行直前）、reset 発行直後、発行後 1 フレーム、発行後の予算終了時の 4 点で行う。各点で次を記録する。

| 項目 | 採取範囲 | 方法 |
| --- | --- | --- |
| CPU の PC | PC の値 | CPU 状態の読取り（ハーネス側） |
| CPU の他のレジスタ | A、X、Y、S、P、MPR0〜MPR7 | 同上。MPR は 8 バイト全部 |
| RAM | WRAM 全 8 KiB（バンク `$F8` に対応する配列の全体） | 配列のダンプ。範囲は固定版の WRAM 配列サイズで確認し、ログに記録する |
| ADPCM 状態 | S1（`$180C`）と S2（内部状態一式） | §3.1 の経路。読取りのみ |
| IRQ 状態 | P の I フラグ、IRQ マスクと保留フラグ | P は CPU 状態から読む。IRQ マスクと保留フラグの保持場所は固定版ソースで確認してから記録する。確認できるまでは UNKNOWN と記録し、推測で埋めない。IRQ 関連のバス読取り（`$1402`、`$1403`）は行わない（§10 の B2） |

採取した値は、判定に使わず、そのまま測定ログに残す。期待値との比較は本書の範囲外である。

## 6. 有界の実行予算と timeout（測定前に決める）

本値は測定を打ち切るための上限であり、期待される結果ではない。

| 項目 | 値 |
| --- | --- |
| 1 試行の CPU ステップ上限 | 2,000,000 ステップ |
| 1 試行のフレーム上限 | 300 フレーム |
| 区分成立の確認までの待ち上限 | 60 フレーム（§2.1 の手順 3） |
| 1 試行の壁時計 timeout | 120 秒 |
| 1 プロセスの壁時計 timeout | 600 秒（複数試行を含む場合の全体） |

上限に達した場合は、その試行を区分 `BUDGET_EXCEEDED` または `TIMEOUT` とし、正例・負例のどちらにも含めない。

## 7. 安全な停止条件と失敗時の動作

### 7.1 停止条件（いずれかで即時に打ち切る）

- S1 と S2 が、区分の成立条件（§3.3）を満たさないまま、§6 の待ち上限に達した（`UNOBSERVED_BUSY`）。
- CPU ステップ上限、フレーム上限、壁時計 timeout のいずれかに達した。
- ハーネスが、ゲストの PC を検査用ゲストの範囲外に検出した。
- 固定版 commit、または合成 ROM の hash が、記録済みの値と一致しなかった。
- ログの書込みに失敗した。
- 予期しない例外が発生した。
- ゲストによる ADPCM または IRQ の MMIO アクセスをハーネスが検出した（検出できた場合のみ。検出できない場合は §10 の BLOCKED として扱う）。

### 7.2 失敗時の動作

- 停止条件に当たった試行は、その時点で破棄する。結果は区分名（§3.3、§6）だけを記録し、正例・負例に含めない。
- 同じ実行の中で、パラメータを変えて再試行しない。
- 次の試行は、新しい Geargrafx インスタンスで始める。前の試行の状態を持ち越さない（warm の区分を除く。§8）。
- 終了コードは非 0 とする。失敗を 0 で終えない。
- 停止条件の検出は、後から判定できるように、理由を一語でログに残す。

## 8. 実験区分の定義（起動形態）

| 区分 | 定義 | 含める条件 |
| --- | --- | --- |
| cold | 新しい Geargrafx インスタンスを作り、合成 ROM を読み込み、リセット後に最初の試行を実行する | プロセス内の最初の試行で、インスタンスを新規作成していること |
| warm | 同じ Geargrafx インスタンスを使い、前の試行の後に続けて実行する。インスタンスの再構成はしない | 同一プロセス内で、同じインスタンスを 2 回目以降に使うこと |
| new-process | 同じ ROM と同じ手順で、プロセスを起動し直す | 別プロセスとして起動し、前プロセスの結果を入力に使わないこと |

- §3.3 の区分（PLAY_ACTIVE など）と、本節の区分（cold など）は直交する。両方を試行ごとに記録する。
- `arm-B`（§4.4）は、上の 3 区分と組み合わせて記録するが、正例の集計には入れない。
- 区分の判定に必要な情報（インスタンス作成の有無、プロセス ID、プロセス内の順番）をログに残す。

## 9. 再現性の確認

### 9.1 完全一致（独立した検査結果）

- 区分ごとに 5 回ずつ実行する（cold、warm、new-process で合計 15 回の最小構成）。
- §5 の全採取値（4 点すべて）のバイト単位一致を、独立した検査結果として記録する。
- これは唯一の合否基準にしない。§9.2 の個別判定と併記する。

### 9.2 個別判定項目（測定前に基準を固定する）

各項目は独立に判定する。ある項目が不合格でも、他の項目の判定を隠さない。

| ID | 項目 | 判定基準 |
| --- | --- | --- |
| R1 | busy（区分）成立の観測 | §3.3 の正例条件（T_b と T_r の両方）を満たすこと。TRANSFER_BUSY は BLOCKED のため判定しない |
| R2 | reset 要求の実行 | §4 の `Adpcm::Write` が例外なく完了し、発行時刻がログに記録されていること（値の結果は問わない） |
| R3 | 有界予算内での終了 | §6 の上限に達せず終了していること |
| R4 | 観測データの取得完了 | §5 の 4 点すべてを取得し、ログに記録されていること |
| R5 | 初期化済み領域の再現性 | ハーネスが書いた領域（ADDRESS、LENGTH の設定値、ゲストバイト列 `$3E00` 以降）の、区分内の全回の一致 |
| R6 | 初期値が未確定な領域の差異 | ハーネスが書いていない WRAM の残り、および初期値が確定していない領域。差異は不合格ではなく、差分として記録する（件数と位置） |

- 同じ試行でも、R1〜R5 が合格し、R6 に差異が出ることがある。その場合は両方を記録する。
- R6 の差異は、再現性の欠陥として隠さず、§9.3 の欄に記録する。

| --- | --- | --- | --- | --- | --- | --- |

### 9.4 判定基準の固定

- 本節（§9.1〜§9.3）の基準は、測定の前に確定する。
- 測定後に基準を変更しない。変更が必要になった場合は、既存の測定結果を破棄し、新しい版の契約として記録し直す。

## 10. 観測しない・実行しない項目（BLOCKED）

以下は、#173 の安全条件に抵触するか、副作用を事前に遮断できないため、本契約で観測も実行もしない。

| ID | 項目 | 理由 |
| --- | --- | --- |
| B1 | busy 中の、ゲストによる ADPCM MMIO（`$1808`〜`$180E`）への書込み | 副作用の事前遮断が未達（#173、#365） |
| B2 | IRQ に関わるバス操作（`$1402`、`$1403` の読書き）、IRQ ハンドラ入口の観測 | #173 の IRQ 側の遮断が未達（#366） |
| B3 | 転送中の、デバイス起点の書込み（ブロック転送、DMA） | #367 が OPEN |
| B4 | 任意の PC、先頭 opcode での実行の中断 | #365 が OPEN。中断はフレーム境界またはステップ境界のハーネス側だけで行う |
| B5 | 純正 System Card の `JSR $E030`（AD_RESET 本体）の呼出し | `BLOCKED_ABI`。#173 のゲートも未解除 |
| B6 | CD 側の MMIO（`$1800`〜`$1803`）への操作 | `$1802`、`$1804` は事前阻止不能（#173） |
| B7 | 純正 BIOS、市販 ROM、私有 ROM（`rom/`）の使用 | 禁止（§1） |
| B8 | 割込みの発生を伴う実行（IRQ の許可を CPU 側で行うこと） | #173、#366 |
| B9 | CPU 命令による `$180D`（reset 要求）の書込み | 副作用の遮断が未達。reset 要求はハーネスからのみ行う（§4） |
| B10 | 転送開始の CPU 命令による発行（`ad_trans`、`ad_play` の呼出し） | 純正 callee の ABI が未確定（`BLOCKED_ABI`） |
| B11 | `$0B`（DMA 経路）による転送 busy の成立、および SCSI 信号の設定 | SCSI と CD 側の操作であり、#173 の B3・B6 に抵触（§3.4 の 2） |

BLOCKED の項目は **11 件**（B1〜B11）である。変更前（初版）は 10 件で、B11 を追加した。

加えて、区分 **TRANSFER_BUSY 全体が BLOCKED**（§3.4）である。

## 11. 結果の区分

- 本契約の手順で測定された事実は **MEASURED** と記録する。
- MEASURED は、固定版 Geargrafx、合成 ROM、ハーネスの範囲内の事実である。
- MEASURED を、公開 System Card ABI の **VERIFIED** に昇格させない。実機、第 2 エミュレータ、純正 BIOS での確認がない限り、VERIFIED とは主張しない。
- `release_eligible=false`、`DEV_CALLABLE` 不可を維持する。
- 結果は区分ごとに別々に報告する。PLAY_ACTIVE の PASS を、TRANSFER_BUSY の PASS として報告しない。
- 測定の結果は、本書の期待値を埋めるのではなく、別の結果文書に記録する。

## 12. idle reset（既存）と busy reset（新規）の分離

| 項目 | idle reset（既存） | busy reset（本書の対象） |
| --- | --- | --- |
| 出典 | #294（device 層診断、`pos-reset`）、#403、#404（guest 実装と実コア判定） | 本書（新規） |
| 前提条件 | アイドル（PLAYING = 0、busy なし）から reset | §3.3 の区分ごとの成立条件を T_b と T_r で確認した後に reset |

idle reset の結果を busy reset の結果として数えない。両者は別の観測として記録する。

## 13. 残件（#295）

1. PLAY_ACTIVE の実コア測定（区分 cold、warm、new-process、各 5 回。§9 の判定を併記）。
2. TRANSFER_BUSY の BLOCKED 解除条件（§3.4 の 3 点）の判定。解除できない場合は、転送 busy 中の reset を #295 の範囲外とするか、別の子 Issue に分けるかを判定する。
3. `arm-B`（bit5 を残す要求）の扱いの判定。
4. IRQ マスクと保留フラグの保持場所の確認（§5 の UNKNOWN の解消）。
5. 独立レビュー、CI への配線の判断。
6. 測定結果が出た後の、期待値の判定（本書とは別の文書で行う）。

ROM-Primitive の実装（`ad_reset_busy` の guest 実装など）は、本書の残件 1 と 2 が揃うまで開始しない。
