# EX_GETFNT フォント容量・変換・ROM 配置設計（#707）

設計日: 2026-11-07。親 Issue #42、後継実装 #708 の前提。
対象は DEV 専用として新設する契約であり、System Card の呼出契約の
実測ではない。本書の手法は固定した公開配布ファイルの実測に基づく。
フォント本体・抽出グリフは含めない。合成模様のみで変換仕様を定義する。

監査の詳細は `docs/research/ex-getfnt-font-candidates.md`、
呼出契約は `docs/research/ex-getfnt-contract-research.md` を参照。

## 境界

- 本書でいう ROM は現行の 256 KiB DEV 診断 ROM
  (`tools/build_rom.py`、`src/bank0.cfg`、`src/boot.s`) である。
  `abi: UNVERIFIED`、`release_eligible: false` を維持する。
- 本書の変換・配置は **DEV 専用契約の提案** であり、純正
  System Card のビット配置と一致するとは主張しない。
  純正の寸法・順序・パディングは UNKNOWN である
  （`docs/research/ex-getfnt-contract-research.md` F07–F11）。
- Geargrafx の固定版は `b49ae82a012eade566d72e9d61c9d95a5caa4da3`
  （`tools/dependencies.json`、`docs/system-card-rom.md`）。
  本書では Geargrafx 実行をしない。実コアの確認は NOT_RUN。

## 1. 現行 ROM の実測（出典 HEAD）

出典は `origin/main` の `ed7d2b2`（2026-11-07 取得）。
`build/debug/bios-dev/dev-only-not-compatible-syscard3.pce`
（debug、262,144 bytes）の `dev.map` による。

| 区分 | CPU 位置 | バイト数 | 備考 |
|---|---|---|---|
| APITABLE | `$E000–$E0F2` | 243 | 81 スロット × 3 bytes `JMP`。slot `$20` は `$E060` |
| FALLBACK | `$E100–$E250` | 337 | 非実装 stub（`LDX #slot` + `JMP api_unimplemented`、各 5 bytes） |
| OVERRIDES | `$E2A0–$E7DB` | 1,340 | 現在 14 スロットの DEV 実装。`.s` から直接リンク |
| BOOT | `$F000–$F004` | 5 | `SEI; LDX #$FF; BRA` |
| VECTORS | `$FFF6–$FFFF` | 10 | 5 ベクタ |
| bank0 最大連続空き | `$E7DC–$EFFF`（2,084）と `$F005–$FFF5`（4,081） | — | `$E800–$EFFF`（2,048 bytes）は core-harness オーバーレイの予約（`src/bank0.cfg` の注記）であり、新規 OVERRIDES 配置の上限は `$E7FF` である |
| bank1–31 | ファイル offset `$2000–$3FFFF` | 253,952 | 現在はすべて `$FF`。`build_rom.py:verify_image` はこれを `$FF` と要求する |

bank0 の要素合計（243+337+1,340+5+10 = 1,935 bytes）と
bank0 空き（6,257 bytes）との差は、上記ギャップの合計であり、
bank0 内に日本語フォントを置く余地はない。フォントは bank1 以降を
使うしかない。

CPU 側の初期配置は HuC6280 の既知事実による。
リセットで MPR7=`$00`、他 MPR は未指定（`spec/rom-contract.json`）。
物理バンクは `MPR[logical>>13]*8192 + (logical&8191)`。
Geargrafx の通常 System Card 経路では 32 ファイルバンクが
`physical_bank % 32` で選択される（`docs/system-card-rom.md`）。
歴史的な System Card の容量・物理配置は UNKNOWN である。
本書はこの歴史を根拠にしない。

ROM サイズを増やすこと（例: 512 KiB）は現行の DEV ビルドと
Geargrafx の 262,144 受け付け条件を変更することになり、
`verify_image` や `rom-contract`、manifest の再現性を含む
Owner 決定が必要である。本書は 256 KiB のまま設計する。

## 2. 容量計算（独立再計算）

### 前提（明示）

- 東雲 `shnmk12.bdf` / `shnmk16.bdf`: `CHARS 6,879`
  （JIS X 0208 `ENCODING 0x2121–0x7426`）。実測で
  12 ドット行は 12 行×2 bytes、16 ドット行は 16 行×2 bytes で、
  全文字 `BBX 12 12` / `16 16` である。したがって
  1 文字分は 12×12=24 bytes、16×16=32 bytes である。
- 索引テーブルは `ENCODING`（JIS X 0208 値）をソートし、
  グリフ ID への二分探索に使う。1 エントリ 4 bytes とする
  （`ENCODING` 2 bytes + ID 2 bytes）。グリフの ROM 内
  オフセットは `ID × 32`（16×16）または `ID × 24` / `ID × 32`
  （12×12 の形式次第）で計算し、別途格納しない。
  §5 の配置ではこの ID 形式を正とし、バンク境界を跨ぐ
  グリフを禁止する。24 bytes 形式は 8,192 bytes のバンクが
  24 の倍数でないため、バンクごとに最大 8 bytes の端数
  パディングが必要となり得る（推奨の 32 bytes 統一形式は
  8,192 の倍数でありこの問題はない）。
- Unifont `unifont_jp-18.0.01.bdf.gz`: Plane 0 57,086 字
  （16 幅 49,777 + 8 幅 7,309）、行 16 行、ビットマップ展開後
  合計 1,709,808 bytes（16 幅 1,592,864 + 8 幅 116,944）。
  16×16 固定セルへ展開すると 57,086×32 = 1,826,752 bytes。
- 圧縮率は実測ファイルの統計による。空行率:
  東雲 12 ドット 3.1%（82,548 行中 2,575 行）、
  16 ドット 4.1%（110,064 行中 4,466 行）。
  互いに異なる行パターンは 12 ドット 2,674、16 ドット 10,188。
  異なる全グリフは 6,849（12 ドット）、6,848（16 ドット）で、
  重複（30 前後）のみである。バイトのエントロピーは
  12 ドット 5.76 bits/byte、16 ドット 6.08 bits/byte。
  空行除去・辞書代換では大幅に縮まらない。エントロピー
  符号化の理想下限（現実の RLE よりさらに小さい）でも
  16 ドット全体で約 167 KB、両サイズ全体で約 286 KB となり、
  253,952 bytes を下回らない。

### 3 方式の比較（N=6,879 全字を前提）

| 方式 | 16×16 容量 | 12×12 容量 | 両サイズ合計 | 索引 4 bytes | 合計目安 | bank1–31（253,952）との比較 |
|---|---|---|---|---|---|---|
| A. 全対象文字を非圧縮で収録 | 220,128 | 165,096 | 385,224 | 27,516 | 412,740 | 超過（159 KB 超） |
| B. 全対象文字を圧縮で収録（理想下限） | 約 167 KB | 約 119 KB | 約 286 KB | 27,516 + 復元 RAM | 約 314 KB | 超過（60 KB 超） |
| C. 段階収録（例: 3,000 字） | 96,000 | 72,000 | 168,000 | 12,000 | 180,000 | 収まる（約 74 KB 余） |

「単に収まりそう」の推測ではなく、式は
`N × (行数 × 2)` であり、N は実測の `CHARS` 値である。
A 単一サイズのみなら 16×16 で 220,128+27,516=247,644 bytes と
なり、理論上は bank1–31 に入るが、残量は約 6 KB に過ぎず、
索引の型を 3 bytes 化する場合でも制約的である。
12×12 単一なら 165,096+27,516=192,612 bytes と余裕がある。
圧縮方式を採用しても索引・復元用 RAM・速度・スタック・MPR の
影響が残り、両サイズの全字は B でも満たさない。

空行率の低さと多様性の高さ（上記）は、RLE や行辞書化が
圧縮の本命にはならないことを示す。例えば全行を 2 bytes
インデックス化する方式は行当たり 2 bytes の追加で
圧縮量より大きくなり、符号化の複雑さに見合わない。
アクティブ圧縮が必要な場合でも、ROM 内での展開用 RAM
確保（行単位の展開ではなく 220 KB に近い全グリフ領域を
展開することとなり得る）、展開速度（HuC6280 8 ビットで
数百 ms 級の見込み、実測が必要）、MPR 復元の条件など
多くの新規条件が増えることとなり、A よりの節約が小さいため、
本書では B を推奨しない。

結論: 両サイズの全字は A も B も現行 256 KiB に収まらない。
**C（段階収録）のみ現実的**である。最小計画は幹部やかなと
記号を含む数千字の決定的な部分集合を両サイズで収録すること
である。残りの字は安全側の挙動（§4）とする。

## 3. 文字コード対応設計

### 3.1 範囲の整理

- **Shift-JIS の 2 バイト文字**: 先頭 `0x81–0x9F` / `0xE0–0xFC`、
  第 2 `0x40–0x7E` / `0x80–0xFC`。これが #707 の契約主張の
  対象である（`docs/research/ex-getfnt-contract-research.md` F03）。
  純正がこの範囲すべてを扱うかは UNKNOWN である。DEV 契約では
  範囲外をエラーとする。
- **Shift-JIS の 1 バイト文字**: `0x00–0x7F`（ASCII）と
  `0xA1–0xDF`（半角カタカナ、JIS X 0201)。出典は 2 バイト前提で
  あり、1 バイトの扱いは UNKNOWN である。DEV 契約の第 1 フェーズでは
  1 バイトをエラーとし、半角描画は想定しない。東雲の半角 BDF
  （`shnm6x12r.bdf` / `shnm8x16r.bdf`）はその目的にあり、
  将来の別モードで検討できる。
- **JIS X 0208**: 94×94 格子中 6,879 字が東雲に収録される。
  `ENCODING` は JIS X 0208 値である（例: 0x2121 は 8,481 10 進）。
  Shinonome が 6,879 字以外を欠落させる 1,957 文字（8,836−6,879）は
  UNDEFINED として扱う（§4）。
- **Unicode**: Unifont は Unicode 値（`ENCODING 0`–`0xFFFF`）である。
  JIS X 0208 と Unicode の対応は標準の変換表によるが、
  単に sjis を Unicode へ変換すれば互換が成立するとは限らない。
  字形・収録範囲・字成りが異なる。#708 の主候補は東雲であり、
  Unicode 経路は Unifont 採用時のみに用いる。

### 3.2 変換手順（DEV 側の決定的仕様）

DEV 契約は次の順序で変換する。スクリプト上で MSB 先行の 2 バイト
（例: `83 52`）を、呼出側が ZP `LSB first` で渡すため、
`word = ($F9 << 8) | $F8` とする（`docs/research/ex-getfnt-contract-research.md`
F04 の主張に従う DEV 側の規約であり、純正の実測ではない）。

```text
1. Validate SJIS lead: 0x81..0x9F or 0xE0..0xFC.
   Else -> Error DEV_ERR_INVALID_SJIS (率先して書込みなし)
2. Validate SJIS trail: 0x40..0x7E or 0x80..0xFC.
   Else -> Error DEV_ERR_INVALID_SJIS
3. Convert SJIS -> JIS ku/ten -> JIS X 0208 code (enc = ku*256+ten in JIS byte form).
   Conversion is arithmetic (piecewise) exactly as:
   if lead in 0x81..0x9F: ku_base = (lead-0x81)*2+1
   else (0xE0..0xFC): ku_base = (lead-0xE0)*2+63
   Trail range determines parity and ten:
     0x40..0x7E: odd ku, ten = trail-0x40+1
     0x9F..0xDD: even ku, ten = trail-0x9F+1
     0x80..0x9E: odd ku, ten = trail-0x80+64
     0xDE..0xFC: even ku, ten = trail-0xDE+64
   ku = ku_base + (even ? 1 : 0)
   JIS code bytes = (ku+0x20, ten+0x20) -> ENCODING decimal = (ku+0x20)*256 + (ten+0x20)
   [Verify: 0x2121 -> 8481; 0x2422 -> 9250; 0x7421 -> 29729]
4. Search sorted ENCODING table (binary search, HuC6280 implementation is linear
   but requires Host-side verification with Python codecs for all JIS X 0208 pairs)
   If not found -> Error DEV_ERR_UNMAPPED (no write as defined in §4)
5. Map to bank/offset and copy to $FA/$FB buffer per §5.
```

この算術式は Python の `shift_jis` / `euc_jp` コーデックを
参照用実装として JIS X 0208 の有効ペア（6,879 字を対象とする
抽出集合と、標準の割り当てペア全体）で照合して検証すること。
数式単独での保証ではなく、ホストテストで
「生成した表と算術式の一致」を含めて検証する。
JIS X 0208 コードに存在しない行（8,836−6,879）は
存在しない形として扱う。なお lead `0xF0–0xFC` は CP932 の
広い範囲であり、この式で ku=95–120 を導くが、JIS X 0208 の
定義域（ku 1–94）を超えるため `ENCODING` は索引の範囲外となり、
`UNMAPPED` として安全に処理される（衝突は生じない）。

### 3.3 半角カナ・ひらがな・カタカナ・漢字・記号・機種依存

- ひらがな・全角カタカナは JIS X 0208 の ku 4–5 付近であり、
  東雲 12/16 には収録される。System Card 側の収録を
  推測しない。全角カタカナは JIS の 2 バイトで扱う。
- 半角カナは 1 バイト (`0xA1–0xDF`) であり、第 1 フェーズでは
  対象外。将来は半角 BDF （6×12 / 8×16）を 12/16 セルへ
  中央配置する DEV 拡張を検討できるが、本書では設計のみ
  とし、純正の半角扱いと混同しない。
- 漢字は JIS X 0208 の Level 1/2 文字であり、収録は
  東雲の 6,879 字の範囲に限る。System Card の漢字と字形が
  一致することは UNKNOWN である。
- 記号・機種依存文字は JIS X 0208 の ku 1–47 等に含まれ、
  東雲の範囲で収録されるものは対象である。未収録記号は
  未収録として扱う。

### 3.4 対応表（形式・生成・容量）

- 形式: `(ENCODING, glyph_id)` の順序保持テーブル。
  エントリは 4 bytes（`ENCODING` 2 + ID 2）である。
  バンク導出は `offset = glyph_id × stride` の商（bank）・
  余り（bank 内オフセット）で計算し、境界を跨ぐグリフを禁止する。
- 生成: BDF の `ENCODING` を読んでソートし、Python で生成する。
  再生成一致をホストテストで確認する。入力版は固定した
  tarball SHA と BDF SHA である（候補監査文書の正本と固定版の章）。
- 容量: 6,879 字で 27,516 bytes。3,000 字で 12,000 bytes。
  全字の稠密テーブルは `0x2121–0x7426` の 21,254 格子中
  6,879 のみであり、稠密化は 21,254×32 680 KB となり不可能であるため、
  疎テーブルが必須である。

## 4. 出力形式の提案（DEV 専用）

### 4.1 BDF から確定できる内容

- 東雲 12/16 の BDF は全グリフ `BBX`/`DWIDTH` がセル全体である。
  `BBX 12 12 0 -2` / `16 16 0 -2` の `x_offset=0`、
  `y_offset=-2`（ベースラインが下から 2 行目）は、BDF の送出順が
  上から下への行列として正しいことを意味する。`BITMAP` の
  hex 文字列がそのまま「上から下」である（BDF 2.1 の仕様どおり）。
- 1 行が 4 hex 文字（2 bytes）であり、左から右へ MSB 順である。
  12 幅の行でも 2 bytes（16 ビット中 12 ビット使用、左寄せ）である。
  16 幅行も 2 bytes（すべて使用）。
- `CHARS 6,879` の全グリフは `DWIDTH 12 0` / `16 0` を持つため、
  幅の情報を保持する追加フィールドは不要である。

### 4.2 DEV 出力の定義（暫定）

以下は DEV 専用の提案であり、純正との一致ではない。
利用者はこれを DEV 契約としてのみ扱うこと。

| 項目 | 16×16（モード 0） | 12×12（モード 1） |
|---|---|---|
| セル寸法 | 16 幅 × 16 高 | 12 幅 × 12 高 |
| 行当たり | 2 bytes | 2 bytes |
| バッファ長 | 32 bytes | **32 bytes**（12 行×2 + 末尾 8 bytes の 0 埋め） |
| 24 bytes / 12 行だけ | — | 代替: 24 bytes（後方互換が必要なら 32 bytes が優先） |
| bit 順序 | 行の上位バイトが左 8 画素、MSB が左端 | 同左 |
| 行順序 | 上から下（BDF 行順） | 同左 |
| パディング | なし | 末尾 8 bytes は 0 |
| 空白文字 | 全 0 | 全 0 |
| 欠落文字 | §4.3（安全側） | §4.3 |

32 bytes 統一を優先する理由は、呼出側がモード切替で
バッファを確保しやすく、純正が 32-byte バッファとされる
出典の主張（`HYPOTHESIS`）と整合するためである。
ただし純正が 24 bytes であった場合に DEV との互換が壊れる点は
UNKNOWN として残す。代替の 24 bytes 形式はホストモデルで
両対応できるが、実機の整合は未確認である。

### 4.3 未収録・空白・欠落の DEV 挙動

- 空白文字（JIS の空白・全角スペース）：東雲は空のビットマップ
  を持つ。DEV はそのまま 0 埋めを出力する。
- 未収録文字・未定義コード：DEV は書込みをしない
  （バッファを汚さない）か、0 埋めをするかを DEV 契約で
  明示する。本書は **書込みなし + エラー戻り値** を提案する。
  呼出側はこの可能性を前提とする。
- 不正 Shift-JIS / 不正モード：書込みなし（§6 の負例）。

### 4.4 Unifont の変換（代替案）

- Unifont の全グリフは 16 行である。`DWIDTH 16` のグリフは
  2 bytes/行でそのままであり、`DWIDTH 8` のグリフは
  1 byte/行で左寄せし、右バイトを 0 とする。
  行幅情報は `DWIDTH` から出るが、DEV 出力は 32 bytes 固定で
  幅を返さないため、呼出側が区別できない。可変幅を表現する
  場合は別仕様が必要である。
- Unifont の `ENCODING` は Unicode 値であり、SJIS→Unicode の
  中間表が必要であり、東雲の JIS 直結より変換が厚い。
  12×12 は存在しないため、16×16 のみになる。

## 5. ROM 配置案

### 5.1 配置（段階収録の例）

| 銀行 | 内容 | 備考 |
|---|---|---|
| bank0 (`$E000–$FFFF`) | 既存の APITABLE / FALLBACK / OVERRIDES / BOOT / VECTORS | 変更なし（slot `$20` は FALLBACK のまま。実装時は OVERRIDES へ移る設計) |
| bank1–bank2 | 索引テーブル（`ENCODING` → グリフ ID） | 3,000 字で 12,000 bytes（2 バンク 16,384 bytes に収まる。1 バンク 8,192 bytes では収まらない）。残量は表の余白。ID は 16 ビット（0–6,878）であり、4 bytes エントリは `ENCODING` 2 + ID 2 である |
| bank3 以降 | グリフデータ | 16×16 領域と 12×12 領域を別々に置く。3,000 字で 96 KB（16 幅）と 72 KB（12 幅、24 bytes 形式）または 96 KB（12 幅、32 bytes 統一形式、§4.2 の推奨）。バンク内オフセットで管理し、バンク境界を跨ぐグリフを禁止 |

索引は 2 サイズで共通の単一テーブルである。
`ENCODING` のソート順の位置がそのままグリフ ID となり、
グリフオフセットは `ID × 32`（16×16）と `ID × 24` または
`ID × 32`（12×12 の形式次第）で計算する。
したがって 2 サイズ分の索引は不要であり、上記の容量表は
単一索引で正しい。別々の `index_16` / `index_12` を持たせると
索引が倍増し、全字で 55,032 bytes、3,000 字で 24,000 bytes となり、
容量表と食い違うため採用しない。

### 5.2 バンク切替と MPR 復元

- 呼出時の MPR7 は既存の銀行配置で固定する（リセット MPR7=`$00`）。
  フォント訪問は別 MPR を使用し、切替前後で保存・復元する。
- MPR6（`$C000–$DFFF`）が自由である場合を優先し、
  バッファ MSB が `$C0` 以上でフォント窓と重なる場合は
  MPR3（`$6000–$7FFF`）へ切り替える（S5 改変の選択を参考にしつつ、
  DEV 側の新規選択として独自に定義する）。MPR の変更は
  呼び出し前後の IRQ ハンドラに影響する可能性があるため、
  DEV 契約では IRQ 時の MPR 状態を保存・復元すること。
- SP の利用は 2 bytes（戻り先）+ フォント切替用 1–2 bytes に
  限定し、スタック境界（`$2100–$21FF` の物理位置は MPR1 依存）
  で割れないこと。SP 境界の試験は §6 の負例に含める。
- `verify_image` は現行で bank1–31 をすべて `$FF` とする。
  #708 では bank1 以降にフォントを含む構成へ変更し、
  `tools/build_rom.py` の検証ロジックも更新が必要である。
  フォントデータは `.bin` のまま格納すると provenance ガード
  （`tools/provenance_guard.py` の禁止拡張子）で拒否されるため、
  変換器で生成する `.s` テーブル（`.byte`/`.word`）として
  リポジトリへ取り込む設計とし、`.incbin` の直格納はしない。

## 6. 合成テスト設計（著作権上問題のない独自模様のみ）

### 合成グリフ（本プロジェクトの独自データ）

以下は東雲・Unifont の抽出ではない。ホストモデルと実機テストの
期待値を共有する合成パターンである（2 bytes/行、MSB 左端）。
24 bytes / 32 bytes の区別は末尾の 0 埋めの有無のみで表す。

| 名前 | 12×12（12 行） | 16×16（16 行） | 意図 |
|---|---|---|---|
| SYN-B | 全 0 | 全 0 | 空白 |
| SYN-A | 毎行 `F0 00`（上位 4 画素のみ） | 毎行 `F0 00` | 左端テスト |
| SYN-B2 | 行ごとに `80 00` / `40 00` / `20 00` / `10 00` を 4 行循環 | 行ごとに `80 00` / `40 00` / `20 00` / `10 00` を 4 行循環 | bit 位置の識別 |
| SYN-C | 行 N が `00 (N*251)` などの決定的模様 | 行 N が `00 (N*251)` などの決定的模様 | 順序・境界 |
| SYN-D | 1 行目のみ非 0（`FF 00`）ほか 0 | 1 行目のみ非 0（`FF 00`）ほか 0 | 先頭行のみの検出 |
| SYN-E | 最終行のみ非 0 | 最終行のみ非 0 | 末端行の検出 |

期待値は疑似乱数ではなく、上記の式から全バイトを
決定できる。これらの合成マップは東雲の BDF と無関係である。

### 正例（ホストモデル + 実機）

| ID | 検証 | 入力（DEV 契約） | 期待 |
|---|---|---|---|
| POS-12 | 12×12 取得 | 有効 SJIS（合成 ID の SJIS 値）・モード 1・バッファ 32 bytes | 上記 SYN の 24 bytes + 末尾 8 bytes 0 と見た目が一致。MPR/SP 保存 |
| POS-16 | 16×16 取得 | 有効 SJIS・モード 0・バッファ 32 bytes | SYN の 32 bytes と一致 |
| POS-BLK | 空白 | 空白の SJIS | 全 0 |
| POS-HIRA | ひらがな | SJIS でひらがなの範囲（合成） | 決定的な SYN（HIRA 代用） |
| POS-KANA | カタカナ | SJIS でカタカナの範囲（合成） | SYN |
| POS-KANJI | 漢字 | SJIS で漢字の範囲（合成） | SYN |
| POS-BIT | bit 並び | SYN-B2 各行 | 左端画素の順序が一致 |
| POS-BND | 出力境界 | バッファ終端近傍 | バッファ外書込みなし |
| POS-SEQ | 連続取得 | 複数 SJIS の連続 | 各呼出の出力が独立し、バッファが汚染されず、MPR/SP を保存 |

### 負例（ホストモデル + 実機）

| ID | 検証 | 入力 | 期待 |
|---|---|---|---|
| NEG-SJIS | 不正 SJIS | 先頭が範囲外・第 2 が範囲外 | 書込みなし、エラー戻り値 |
| NEG-UNDEF | 未定義コード | 有効範囲だが JIS にない（例: ku/ten の未割り当て） | 書込みなし、エラー戻り値 |
| NEG-UNMAP | 未収録文字 | JIS にはあるが索引にない | 書込みなし、エラー戻り値 |
| NEG-MODE | 不正モード | `$FF` = 2, 3, 255 | 書込みなし、エラー戻り値。`FNTERR` への迂回は純正 DEV でも定義しない |
| NEG-SIZE | 出力先不足 | 32 bytes を確保できないバッファ | 書込みなし、エラー戻り値（境界試験） |
| NEG-RAM | RAM 範囲超過 | 出力先が RAM 範囲外（例: ROM/IO 領域） | 書込みなし、エラー戻り値 |
| NEG-MPR | MPR 境界 | バッファがフォント窓と重なる | 窓の切替で正しく書込み、正しく復元 |
| NEG-BANK | バンク切替失敗 | フォントバンクの MPR 不正 | 書込みの部分的成功をしない、エラー戻り値 |
| NEG-STACK | スタック破壊 | SP がスタック下限周辺 | 割れないこと、戻り値の保存 |
| NEG-OVER | バッファ外書込み | バッファ長境界の厳密試験 | バッファ外への書込みゼロ |

### 合否条件（将来 #708）

- ホスト fixture（Python モデルと生成表の照合）で
  正例・負例の期待値が全量一致し、負例でバッファ内が
  変更されていないこと。
- pinned Geargrafx 実コアで合成 caller → DEV callee → 出力の
  全量比較・エラー時無破壊・MPR/SP/IRQ を記録し、
  ホスト成功と実コア成功を区別すること。
- 純正の模様との一致は合否条件にしない（UNKNOWN のため）。
- 未実行は NOT_RUN、不足は BLOCKED とする。合成テストの
  合否は純正互換の証拠ではない。

## 7. #708 の最小実装範囲と開始条件

### 推奨

- **フォント**: 東雲 Gothic Medium Regular の 12/16 固定長
  （tarball `shinonome-0.9.11p1.tar.bz2`、SHA 固定）。
  Unifont は主候補から外す。
- **対応サイズ**: 12×12 と 16×16 の両対応（32 bytes 統一）。
- **ライセンス**: 東雲の実質 PD の宣言 + LICENSE/AUTHORS の
  NOTICE 保持を条件に `CONDITIONAL`。MIT との関係は
  本リポジトリの MIT LICENSE は自ら所有または許諾を受けた部分に
  のみ適用されることを明確にし、フォント部分は別文とする。
- **変換方式**: §3 の SJIS→JIS 算術 + ソート済み索引二分探索
  （ホストモデルは Python codecs を参照）。
- **出力形式**: 2 bytes/行、上から下、MSB 左端、12×12 は
  末尾 8 bytes 0 埋めの 32 bytes。
- **ROM 配置**: §5（bank1–bank2 索引、bank3 以降グリフ、MPR6/MPR3 切替）。
- **最小実装範囲**: 段階収録の部分集合（LEVEL 1 漢字＋かな＋
  記号など数千字を Owner が選定）から始め、9 行目の字を
  1 字ずつ確認する。両サイズの変換器と実コア試験を先に固める。
- **最初の実装単位**: ホスト変換器（BDF→索引・グリフ表の決定的生成
  と再生成一致）→ host Python モデル → DEV ROM への bank1–31 格納
  と `build_rom.py` の検証更新 → DEV callee の最小実装
  （正例のみ）→ 実コア負例への拡張 の順序。

### 残存 UNKNOWN と Owner 判断事項

- 純正のビット順・行順・パディング・戻り値・保存レジスタ
  （F07–F17）は UNKNOWN のままである。DEV 契約はこの UNKNOWN を
  デザインで置き換えるものであり、System Card 互換の主張ではない。
- Owner は以下を #708 開始条件として判断する:
  1. 東雲 2 ファイルの `#708` 実開発への承認（要町-改と jiskan16 由来の承知を含む）。
  2. 12×12 の 32 bytes 統一（vs 24 bytes）の採用。
  3. 段階収録の文字範囲（Level 1 等）の確定。
  4. `tools/build_rom.py` の bank1–31 検証変更と provenance ガード
     （`.bin` 格納不可）への `.s` テーブル生成設計への承認。
- 承認が得られるまで、フォントの取り込み・ROM 配線・ライセンスの
  使用はしない。未承認は `PENDING` のままである。
