# Issue #295: AD_RESET の busy 境界の観測契約（測定手順の固定）

親 #25。前提 PR: #403（`ad_reset_idle` guest 実装）、#404（idle 実コア観測ドライバ）は main に統合済み。関連: [ad-reset-diagnostic.md](ad-reset-diagnostic.md)（#294、idle と play の device 層診断）、[ad-reset-contract.md](ad-reset-contract.md)（#292、ABI 台帳）、[ad-reset-fixture.md](ad-reset-fixture.md)（#293、合成 fixture）。

**状態: 契約のみ。実コア測定は未実施。`BLOCKED_ABI`、`release_eligible=false`、`DEV_CALLABLE` 不可。System Card 互換の VERIFIED とは主張しない。**

本書の目的は、実測の前に測定手順を固定することである。reset 後のフラグ、RAM、IRQ、転送の中断結果などの期待値は、本書では決め打ちしない。期待値を含む判定は、測定ログを取得した後に別文書で行う。

## 2. busy 状態を成立させる操作（確認手順）

本節は「busy が立つと想定する操作」ではなく、busy を確認するための手順である。成立したかどうかは §3 の観測で判定する。

1. ハーネスは、device 層の `Adpcm::Write` だけで ADPCM を設定する（CPU 命令経由の MMIO 書込みは使わない）。
   - ADDRESS と LENGTH は、本書で固定した値（`ADDRESS = $1234`、`LENGTH = $0400`）を書く。
   - CONTROL に再生・転送の開始ビット（bit5）を含む値を書く。#294 の `neg-reset-playing` と同じ経路である。
2. `RunToVBlank` で 1 フレームずつ進め、§3 の観測点で busy を確認する。
3. 確認できるまで最大 60 フレームまで待つ（§6）。確認できない試行は busy reset の正例に含めない（§3.3）。

## 3. busy 成立の観測点

### 3.1 観測する状態

| 観測点 | 読む対象 | 経路 | 副作用 |
| --- | --- | --- | --- |
| S1: ステータス | ADPCM_STAT（`$180C`） | device 層の `Adpcm::Read`（ハーネス側） | なし。`Read($0A)` は副作用があるため呼ばない（#294） |
| S2: 内部状態 | ADDRESS、READ/WRITE_ADDRESS、LENGTH、PLAYING、busy カウンタ | `Adpcm::GetState()`（読取りのみ） | なし |
| S3: 時刻 | 経過フレーム数、CPU ステップ数 | ハーネスのカウンタ | なし |

busy を示すステータスのビットは、#294 の診断文書で `$04`、`$80` と記録されているが、これは固定版ソースから読んだ候補であり、busy ビットとしての確認は測定で行う（本書では確定値として扱わない）。

### 3.2 観測の時点

- T_b（busy 確認時）: S1 と S2 を同時に読む。1 フレーム進めた後に読む。
- T_r（reset 発行直前）: S1 と S2 を再び読む。T_b と T_r の両方で busy が観測されていることを、正例の条件とする。

### 3.3 観測できない試行の扱い

- T_b または T_r のいずれかで busy を観測できなかった試行は、区分 `UNOBSERVED_BUSY` とする。
- `UNOBSERVED_BUSY` の試行は busy reset の正例に含めない。負例にも含めず、件数だけを報告する。
- 「観測できないのに busy と見なす」ことは禁止する。内部状態だけが busy を示し、S1 が示さない場合も `UNOBSERVED_BUSY` とする。

## 4. reset 要求の発行方法（手順のみ）

1. T_r の時点（フレーム境界）で、ハーネスが `Adpcm::Write` を 1 回だけ呼ぶ。書込み先は CONTROL（`$180D`）、値は `$80`（bit7 = 1、bit5 = 0）とする。
2. reset 要求はハーネスからのみ発行する。CPU 命令による `$180D` への書込みは行わない（§10 の B9）。
3. reset の発行は 1 試行につき 1 回とする。再発行はしない。
4. 別系統として、bit5 を 1 のまま残す値（`$A0`）での要求を、区分 `arm-B` として別に測る。`arm-B` は正例の集計に入れない。

## 5. reset 前後で採取する範囲

採取は T_r（発行直前）、reset 発行直後、発行後 1 フレーム、発行後の予算終了時の 4 点で行う。各点で次を記録する。

| 項目 | 採取範囲 | 方法 |
| --- | --- | --- |
| CPU の PC | PC の値 | CPU 状態の読取り（ハーネス側） |
| CPU の他のレジスタ | A、X、Y、S、P、MPR0〜MPR7 | 同上。MPR は 8 バイト全部 |
| RAM | WRAM 全 8 KiB（バンク `$F8` に対応する配列の全体） | 配列のダンプ。範囲は固定版の WRAM 配列サイズで確認し、ログに記録する |
| ADPCM 状態 | S1（`$180C`）と S2（内部状態一式） | §3.1 の経路。読取りのみ |
| IRQ 状態 | P の I フラグ、固定版コアの IRQ マスクと保留フラグ | コアの内部状態を読む。IRQ 関連のバス読取り（`$1402`、`$1403`）は行わない（§10 の B2） |

採取した値は、判定に使わず、そのまま測定ログに残す。期待値との比較は本書の範囲外である。

## 6. 有界の実行予算と timeout（測定前に決める）

本値は測定を打ち切るための上限であり、期待される結果ではない。

| 項目 | 値 |
| --- | --- |
| 1 試行の CPU ステップ上限 | 2,000,000 ステップ |
| 1 試行のフレーム上限 | 300 フレーム |
| busy 確認までの待ち上限 | 60 フレーム（§2 の手順 3） |
| 1 試行の壁時計 timeout | 120 秒 |
| 1 プロセスの壁時計 timeout | 600 秒（複数試行を含む場合の全体） |

上限に達した場合は、その試行を区分 `BUDGET_EXCEEDED` または `TIMEOUT` とし、正例・負例のどちらにも含めない。

## 7. 安全な停止条件と失敗時の動作

### 7.1 停止条件（いずれかで即時に打ち切る）

- S1 が busy を示さないまま、§6 の busy 確認の上限に達した（`UNOBSERVED_BUSY`）。
- CPU ステップ上限、フレーム上限、壁時計 timeout のいずれかに達した。
- ハーネスが、ゲストの PC を検査用ゲストの範囲外に検出した。
- 固定版 commit、または合成 ROM の hash が、記録済みの値と一致しなかった。
- ログの書込みに失敗した。
- 予期しない例外が発生した。
- ゲストによる ADPCM または IRQ の MMIO アクセスをハーネスが検出した（検出できた場合のみ。検出できない場合は §10 の BLOCKED として扱う）。

### 7.2 失敗時の動作

- 停止条件に当たった試行は、その時点で破棄する。結果は区分名（§3.3、§6）だけを記録し、正例・負例に含めない。
- 同じ実行の中で、パラメータを変えて再試行しない。
- 次の試行は、新しい Geargrafx インスタンスで始める。前の試行の状態を持ち越さない（warm の区分を除く。§8）。
- 終了コードは非 0 とする。失敗を 0 で終えない。
- 停止条件の検出は、後から判定できるように、理由を一語でログに残す。

## 8. 実験区分の定義

| 区分 | 定義 | 含める条件 |
| --- | --- | --- |
| cold | 新しい Geargrafx インスタンスを作り、合成 ROM を読み込み、リセット後に最初の試行を実行する | プロセス内の最初の試行で、インスタンスを新規作成していること |
| warm | 同じ Geargrafx インスタンスを使い、前の試行の後に続けて実行する。インスタンスの再構成はしない | 同一プロセス内で、同じインスタンスを 2 回目以降に使うこと |
| new-process | 同じ ROM と同じ手順で、プロセスを起動し直す | 別プロセスとして起動し、前プロセスの結果を入力に使わないこと |

- 区分は試行ごとに記録する。区分が混ざった集計は行わない。
- `arm-B`（§4.4）は、上の 3 区分と組み合わせて記録するが、正例の集計には入れない。
- 区分の判定に必要な情報（インスタンス作成の有無、プロセス ID）をログに残す。

## 9. 再現性の確認

- 区分ごとに 5 回ずつ実行する（cold、warm、new-process で合計 15 回の最小構成）。
- 一致基準は次の 3 つとする。
  1. 各回の終了コードが 0 である。
  2. 同じ区分の中で、§5 の全採取項目（4 点すべて）がバイト単位で一致する。
  3. 合成 ROM と固定版 commit の hash が、全回で同一である。
- 区分をまたぐ比較は情報として記録するが、一致を要求しない。
- 1 回でも一致基準を外した区分は、その区分の結果を「再現せず」と記録し、正例として使わない。

## 10. 観測しない・実行しない項目（BLOCKED）

以下は、#173 の安全条件に抵触するか、副作用を事前に遮断できないため、本契約で観測も実行もしない。

| ID | 項目 | 理由 |
| --- | --- | --- |
| B1 | busy 中の、ゲストによる ADPCM MMIO（`$1808`〜`$180E`）への書込み | 副作用の事前遮断が未達（#173、#365） |
| B2 | IRQ に関わるバス操作（`$1402`、`$1403` の読書き）、IRQ ハンドラ入口の観測 | #173 の IRQ 側の遮断が未達（#366） |
| B3 | 転送中の、デバイス起点の書込み（ブロック転送、DMA） | #367 が OPEN |
| B4 | 任意の PC、先頭 opcode での実行の中断 | #365 が OPEN。中断はフレーム境界またはステップ境界のハーネス側だけで行う |
| B5 | 純正 System Card の `JSR $E030`（AD_RESET 本体）の呼出し | `BLOCKED_ABI`。#173 のゲートも未解除 |
| B6 | CD 側の MMIO（`$1800`〜`$1803`）への操作 | `$1802`、`$1804` は事前阻止不能（#173） |
| B7 | 純正 BIOS、市販 ROM、私有 ROM（`rom/`）の使用 | 禁止（§1） |
| B8 | 割込みの発生を伴う実行（IRQ の許可を CPU 側で行うこと） | #173、#366 |
| B9 | CPU 命令による `$180D`（reset 要求）の書込み | 副作用の遮断が未達。reset 要求はハーネスからのみ行う（§4） |
| B10 | 転送開始の CPU 命令による発行（`ad_trans`、`ad_play` の呼出し） | 純正 callee の ABI が未確定（`BLOCKED_ABI`） |

BLOCKED の件数は **10 件**（B1〜B10）である。

## 11. 結果の区分

- 本契約の手順で測定された事実は **MEASURED** と記録する。
- MEASURED は、固定版 Geargrafx、合成 ROM、ハーネスの範囲内の事実である。
- MEASURED を、公開 System Card ABI の **VERIFIED** に昇格させない。実機、第 2 エミュレータ、純正 BIOS での確認がない限り、VERIFIED とは主張しない。
- `release_eligible=false`、`DEV_CALLABLE` 不可を維持する。
- 測定の結果は、本書の期待値を埋めるのではなく、別の結果文書に記録する。

## 12. idle reset（既存）と busy reset（新規）の分離

| 項目 | idle reset（既存） | busy reset（本書の対象） |
| --- | --- | --- |
| 出典 | #294（device 層診断、`pos-reset`）、#403、#404（guest 実装と実コア判定） | 本書（新規） |
| 前提条件 | アイドル（PLAYING = 0、busy なし）から reset | busy を §3 で確認した後に reset |
| 観測済みの範囲 | 実コアで PASS（合成 BIOS、合成 CD）。ログの hash は各 PR 本文に記録 | 未観測。本書は手順のみ |
| 正例の定義 | §3 の観測がアイドルを示すこと | §3.2 の T_b と T_r の両方で busy を観測すること |
| 扱い | 既存の検証として参照する。本書では再測定しない | 本書の手順に従って新規に測定する。結果が出るまでは未検証 |
| 区分 | cold、warm、new-process のうち実施済みの区分のみ | §8 の 3 区分すべて |
| 残件 | 独立レビュー未実施、CI 未配線（#404 本文） | 測定、独立レビュー、必要なら別子 Issue での扱いの判定 |

idle reset の結果を busy reset の結果として数えない。両者は別の観測として記録する。

## 13. 残件（#295）

1. 本書の手順に従う busy reset の実コア測定（区分 cold、warm、new-process、各 5 回）。
2. `arm-B` の扱いの判定（bit5 を残す要求が busy 境界にどう影響するか）。
3. 残りの範囲（転送中の busy からの reset）が #295 に含まれるか、別子 Issue に分けるかの判定。Issue の棚卸しでは、この判定まで OPEN と記録されている。
4. 独立レビュー、CI への配線の判断。
5. 測定結果が出た後の、期待値の判定（本書とは別の文書で行う）。

ROM-Primitive の実装（`ad_reset_busy` の guest 実装など）は、本書の残件 1 と 3 が揃うまで開始しない。
