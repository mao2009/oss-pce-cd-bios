## 1. 基本設計：ROM 格納と DEV RAM 出力

今回の基本設計は以下とする。

| サイズ | ROM 格納 | DEV RAM 出力 |
|---|---|---|
| 12×12 | 24 bytes | 32 bytes |
| 16×16 | 32 bytes | 32 bytes |

12×12 について:

- 1bpp、1 行 12 ピクセル。1 行を 2 バイトに格納し、12 行×2 = 24 bytes。
  各行の未使用 4 ビットはゼロとする。行の上位 12 ビットが有効画素であり、
  下位 4 ビットはゼロである。BDF の行ビットは 2 バイトで左寄せであるため、
  この定義は正規化を意味する（§5.5）。
- RAM へ転送する際は 24 バイトをコピーし、末尾 8 バイトはゼロで埋める。
  合計 32 バイトの DEV 専用固定長出力とする。
- 32 バイト統一は独自 DEV 契約であり、純正の仕様ではない。純正の
  12×12 出力が 24 バイトか 32 バイトか、行順・パディング・レジスタ保存・
  エラー動作などは UNKNOWN のまま維持する。商用ゲームのバッファへ
  無条件に 32 バイト書くことは禁止する（§6.2）。

16×16 について:

- 1bpp、1 行 16 ピクセル。1 行 2 バイト×16 行 = 32 bytes。余分な
  ゼロ埋めは行わない。ROM の 32 バイトをそのまま RAM へ転送する。

ため Owner 決定が必要である。本書は 256 KiB のまま設計する。

## 3. ROM 容量の再計算（3,000 字を基準）

### 3.1 理論容量

3,000 字の段階収録について:

- 12×12: 3000×24 = 72,000 bytes（生データ）
- 16×16: 3000×32 = 96,000 bytes（生データ）
- 共通索引: 3000×4 = 12,000 bytes
- 理論上の合計: 180,000 bytes
- bank1–31 の空き: 253,952 bytes
- 理論上の残量: 73,952 bytes

73,952 bytes は理論上の残量であり、最終的な空きを保証する数値ではない。
次節で区別する 7 項目が理論値との差を生む。

### 3.2 7 項目の区別

1. **生データ**: 72,000 + 96,000 = 168,000 bytes。
2. **バンク境界のパディング**: 24 バイトグリフはバンク境界を跨ぐ可能性がある。
   8,192 bytes のバンクに 24 バイトの何個が入るかは 8,192 を 24 で割った値に
   依存する。341 個で 8,184 bytes となり、残り 8 bytes である。バンク跨ぎを
   禁止する配置では、バンクごとに最大 8 bytes の余りが生じる。
3. **アラインメント**: 索引（4 bytes/エントリ）は 8,192 を 4 で割れるため
   バンク内で整列し、余りはバンク末尾の端数だけである。グリフ領域は
   開始バンクを揃える。
4. **索引の配置領域**: 索引は bank1–bank2（2 バンク）に配置する。
   12,000 bytes は 1 バンク（8,192 bytes）には収まらず、2 バンク
   （16,384 bytes）で収まる。割り当ては 16,384 bytes であり、
   生データ超の分 4,384 bytes は余りである。
5. **ROM マッピング処理に必要な追加テーブル**: バンク導出のための
   追加表は本設計では設けない。グリフ ID からバンク・オフセットを
   算術で導く（§3.3）。表を設ける場合の分は本節の見積りには含めない。
6. **BIOS コードの増加分**: 新規の DEV コードは先頭バンクの OVERRIDES に入る。
   bank1–31 のフォント領域とは別枠であり、bank1–31 の残量を減らさない。
   先頭バンクのコード領域は予約で上限が厳しいため、コード増加の可否は
   別途検証が必要である（本節では bank1–31 の実効残量のみを述べる）。
7. **実際に使用可能な残量**: 上記 1–6 を反映した割り当て後の残量である。
   §3.4 に示す。

### 3.3 バンク整列とグリフ ID から ROM アドレスの導出

グリフ ID は索引ソート順の位置である（0 から開始）。

12×12（stride 24、バンク境界跨ぎ禁止）:

- 1 バンクに収まる数: `8192 // 24 = 341` 個（使用 8,184 bytes、余り 8 bytes）。
- ID のバンク内位置: `bank_within = id // 341`、`pos = id % 341`。
- バンク内オフセット: `pos * 24`。ファイルオフセットは
  `region_base_bank * 8192 + bank_within * 8192 + pos * 24` である。
- 無条件の `id * 24` は使えない。`id=341` の無補正オフセットは 8,184 で
  バンク内に収まるが、`id=342` の無補正は 8,208 となりバンクを跨ぐ。
  バンク補正では `id=341` は次バンク先頭（`bank_within=1, pos=0, offset=0`）、
  `id=342` は `bank_within=1, pos=1, offset=24`（領域内 8,216）になり、
  無補正（8,208）と 8 bytes 食い違う。バンクごとに 341 個で区切り、
  末尾 8 bytes を空けることで跨ぎを防ぐ。

16×16（stride 32、境界跨ぎなし）:

- 1 バンクに 256 個（8,192 を 32 で割れる）。バンク補正は
  `bank_within = id // 256`、`pos = id % 256`、`offset = pos * 32` であり、
  無条件の `id * 32` でも領域内オフセットは一致する。ただし
  ファイルバンク番号は領域の基底バンクを加えて導く。

索引（4 bytes/エントリ）:

- 1 バンクに 2,048 個（8,192 を 4 で割れる）。3,000 字では
  2 バンクで収まる。バンク補正は `id // 2048` と `id % 2048` である。

低レベルのバンク計算は文字数を受け取らず、最大 ID 超過を判定できない。
そのため DEV 実装は文字数・割当バンク数を検証する上位関数を必ず用いる。
上位関数は `id<0` を拒否し、`id>=glyph_count` を拒否し、導出したバンクが
割当範囲を超えないことと、バンク内オフセット＋グリフ長が 8KiB 以内に
収まることを検証する。呼出側は低レベル関数を直接用いず上位関数を用いる。

### 3.4 実効配置（3,000 字）

| 領域 | 割り当て | バンク数 | 生データ | 余り |
|---|---|---|---|---|
| 索引（bank1–bank2） | 16,384 | 2 | 12,000 | 4,384 |
| 16×16（bank3–bank14） | 98,304 | 12 | 96,000 | 2,304 |
| 12×12（bank15–bank23） | 73,728 | 9 | 72,000 | 1,728 |
| 合計割り当て | 188,416 | 23 | 180,000 | 8,416 |
| bank1–31 の残り | 65,536 | 8 | — | — |

16×16 は 256 個/バンクで 3,000 字は 12 バンク（11*256=2816、残り 184 字で
1 バンク）である。12×12 は 341 個/バンクで 3,000 字は 9 バンク
（8*341=2728、残り 272 字で 1 バンク）である。
実効残量は 65,536 bytes（8 バンク分）であり、理論残量 73,952 bytes から
8,416 bytes を差し引いた値である。最終的な空きは、この割り当て後に
固まる。BIOS コードの増加分は先頭バンク側で別途検証する。

全字（6,879 字）の参考値: 16×16 は 27 バンク（221,184 bytes 割り当て）、
12×12 は 21 バンク（172,032 bytes 割り当て）、索引は 4 バンク
（32,768 bytes 割り当て）となり、合計 52 バンク超で bank1–31（31 バンク）に
収まらない。両サイズ全字は A も圧縮（理想下限でも約 314 KB）も満たさない。
段階収録のみ現実的である。

空行率（12 ドット 3.1%、16 ドット 4.1%）とエントロピー（5.76 / 6.08 bits/byte）は、
空行除去や辞書化で大幅に縮まないことを示す。圧縮は推奨しない。

## 4. 文字コード対応設計

### 4.1 範囲の整理

- **2 バイト文字**: 先頭 129–159 / 224–252、第2 64–126 / 128–252。
  これが契約主張の対象である。純正がこの範囲すべてを扱うかは UNKNOWN であり、
  DEV 契約では範囲外をエラーとする。
- **1 バイト文字**: 0–127 と 161–223（半角カタカナ）。出典は 2 バイト前提であり、
  1 バイトの扱いは UNKNOWN である。DEV の第 1 フェーズでは 1 バイトをエラーとし、
  半角描画は想定しない。
- **JIS X 0208**: 94×94 の区点格子に 8,836 位置が存在し、そのうち 6,879 字が
  東雲に収録される。`ENCODING` は JIS 値である（例: 8481 は最初の登録値）。
  8,836 は格子位置の総数であり、すべてに文字が割り当てられた数を意味しない。
  差分 1,957 は「JIS の未割当位置＋フォントの未収録」を混同した値として扱わず、
  未割当位置とフォント未収録は別々に扱う。Shift-JIS が表現できる範囲と、
  JIS に実際に割り当てられた文字の集合は混同しない。
- **Unicode**: Unifont は Unicode 値である。単に変換すれば互換が成立するとは限らない。
  主候補は東雲であり、Unicode 経路は Unifont 採用時のみに用いる。

### 4.2 変換手順（DEV 側の決定的仕様）

DEV 契約は次の順序で変換する。文字コードワードは呼出側の入力から得る
（具体的な保持位置の数値は本書では定めず、DEV 実装側で別途定義する。
純正の保持位置と混同しない）。

```text
1. Validate SJIS lead: 0x81..0x9F or 0xE0..0xFC. Else -> Error INVALID_SJIS (no write)
2. Validate SJIS trail: 0x40..0x7E or 0x80..0xFC. Else -> Error INVALID_SJIS
3. Convert SJIS -> ku/ten -> JIS code:
   if lead in 0x81..0x9F: ku_base = (lead-0x81)*2+1
   else (0xE0..0xFC): ku_base = (lead-0xE0)*2+63
   Trail decides parity/ten:
     0x40..0x7E: odd, ten = trail-0x40+1
     0x9F..0xDD: even, ten = trail-0x9F+1
     0x80..0x9E: odd, ten = trail-0x80+64
     0xDE..0xFC: even, ten = trail-0xDE+64
   ku = ku_base + (even ? 1 : 0)
   JIS bytes = (ku+0x20, ten+0x20); ENCODING = (ku+0x20)*256 + (ten+0x20)
   [Examples (decimal): 8481, 9250, 29729]
4. Search sorted ENCODING table. If not found -> Error UNMAPPED (no write)
5. Map ID -> (bank, offset) by §3.3 and copy to output buffer by §6.1.
```

この算術式は Python の `shift_jis` / `euc_jp` を参照用実装として
JIS の有効ペアで照合して検証する。JIS に存在しない行は未定義として扱う。
lead の広い範囲（後段）は ku が定義域を超えるため索引範囲外となり、
`UNMAPPED` として安全に処理される（衝突は生じない）。

### 4.3 半角・かな・漢字・記号

- ひらがな・全角カタカナは JIS の対応範囲であり、東雲 12/16 に収録される。
  純正側の収録を推測しない。全角カタカナは 2 バイトで扱う。
- 半角カナは 1 バイトであり、第 1 フェーズでは対象外。
- 漢字は JIS の範囲に限る。純正との字形一致は UNKNOWN である。
- 記号・機種依存は JIS の範囲で収録されるものを対象とし、未収録は未定義とする。

### 4.4 対応表（形式・生成・容量）

- 形式: `(ENCODING, glyph_id)` の順序保持テーブル。4 bytes（2+2）である。
  バンク導出は §3.3 のバンク補正式による（`bank_within = id // per`、
  `pos = id % per`、`offset = pos * stride`、ここで `per` は stride 依存で
  341 または 256）。境界跨ぎを禁止する。
- 生成: BDF の `ENCODING` を読んでソートし、Python で生成する。再生成一致を
  ホストテストで確認する。入力版は監査文書の正本と固定版の章が正である。
- 容量: 6,879 字で 27,516 bytes。3,000 字で 12,000 bytes。稠密化は不可能である。

## 5. BDF 変換仕様（決定的）

#708 へ引き渡す決定的な変換仕様である。入力は固定版のみとする。

### 5.1 入力の固定版

- 東雲 tarball `shinonome-0.9.11p1.tar.bz2`（監査文書が SHA を固定）。
- 12×12 入力: `bdf/shnmk12.bdf`
- 16×16 入力: `bdf/shnmk16.bdf`
- BDF 個別の SHA は監査文書の監査表が正である。本仕様では再掲しない。

### 5.2 文字索引（ENCODING）

- BDF の各グリフの `ENCODING` を JIS 値の decimal として読む。
- 収集した `ENCODING` を数値順にソートし、重複を取り除かない。
  重複があれば変換器は拒否する（§5.6）。
- ソート順の位置（0 から開始）がグリフ ID である。
  入力順序に依存しない出力とするため、ソート後に ID を付与する。
- 索引は `(ENCODING, glyph_id)` の順序保持テーブルとして生成する。
- 検索はソート済み索引に対する二分探索を正とする。ホストモデルは
  `search_glyph_id(sorted_encodings, encoding)` を用い、存在する場合は
  グリフ ID を返し、存在しない場合は `UNMAPPED` として明示的に拒否する。
  別の ID への代替やグリフデータの返却はしない。正例と未収録拒否は
  同じ関数を通る。#708 の変換器設計はこの二分探索を引き継ぐ。

### 5.3 Shift-JIS から JIS への変換

§4.2 の算術式をそのまま用いる。有効範囲は §4.1 とする。
範囲外は `INVALID_SJIS`、索引にない JIS は `UNMAPPED` として拒否する。

### 5.4 12×12 と 16×16 の対応

- 12×12 と 16×16 の BDF は、同一の `ENCODING` 集合を持つが、
  グリフは別デザインである。同一の ID に対して両サイズの
  グリフが存在しなければならない。片方のみの `ENCODING` は
  変換器の拒否対象とする。
- 12×12 の ROM 格納は 24 bytes のみとし、16×16 は 32 bytes とする。
  RAM 出力への拡張は §6 の DEV 契約による。

### 5.5 BBX・DWIDTH・BITMAP の検証と正規化

- 全グリフについて以下を検証する:
  - `BBX` がセル全体である（12 サイズで 12×12、16 サイズで 16×16）。
  - `DWIDTH` がセル幅を返す（12 または 16、y は 0）。
  - `BITMAP` の行数がセル高に一致する（12 または 16）。
  - 各行の 16 進文字列長が 4 文字（2 バイト）である。
- 不一致は変換器の拒否対象とする。検証は単位テストで確認する。
- 行ビット順とパディングの正規化:
  - 行は上から下の順である。BDF の行順をそのまま用いる。
  - 1 行 2 バイトのうち上位ビットが左端画素である（MSB 左端）。
  - 12×12 の各行は下位 4 ビットをゼロとする。BDF の行は左寄せであるため、
    この正規化は検証とゼロ化で確認する。
  - 16×16 の各行は 16 ビットすべてを有効とする。
  - 余分な行の追加付除去は行わない。

### 5.6 未収録・重複・入力順序・再生成一致

- 未収録文字: 索引にない JIS は `UNMAPPED` として拒否する。
- 重複文字: 同一 `ENCODING` が 2 回現れる入力は拒否する。
- 入力順序に依存しない: ソート後に ID を付与するため、BDF 内の
  グリフ順序が変わっても生成結果は同一である。
- 再生成一致: 同一入力版、同一ソート、同一正規化の条件で生成した
  2 回の結果がバイト一致することをホストテストで確認する。

## 6. 出力形式（DEV 専用）と RAM 出力境界

### 6.1 DEV 出力の定義

| 項目 | 12×12 | 16×16 |
|---|---|---|
| ROM 格納 | 24 bytes（12 行×2） | 32 bytes（16 行×2） |
| RAM 出力 | 32 bytes（24 bytes + 末尾 8 bytes ゼロ） | 32 bytes（コピー） |
| 行当たり | 2 bytes、上位 12 ビット有効、下位 4 ビットゼロ | 2 bytes、全 16 ビット有効 |
| bit 順序 | 上位バイト左 8 画素、MSB 左端 | 同左 |
| 行順序 | 上から下 | 同左 |
| パディング | RAM 末尾 8 bytes ゼロ | なし |

32 バイト統一は独自 DEV 契約であり、純正の仕様ではない。

### 6.2 RAM 出力境界の許可条件

32 バイトの DEV 出力は、以下の条件をすべて満たす場合に限って許可する。

- 呼出し側が 32 バイト以上の書込み可能な領域を確保している。
- 宛先の全 32 バイトが適切な RAM 上にある。
- 宛先が ROM・I/O・禁止領域と重ならない。
- アドレス加算でオーバーフローしない。
- 不正入力時は書込みを行わない。
- 不明な MPR 配置を成功扱いしない。
- 必要な MPR/SP 保存・復元が検証されている。

呼出規約にバッファ長が存在しない場合、BIOS がその確保長を一般には
検証できない。このため初期 DEV 実装の対象は、32 バイト確保を
保証できる合成 caller のみに限る。32 バイト確保を保証できない
呼出しは、成功扱いしない（拒否または別契約とする）。

### 6.3 未収録・空白・欠落

- 空白はビットマップのゼロ行そのものを出力する。
- 未収録・未定義は書込みなし＋エラー戻り値とする。呼出側はこの可能性を前提とする。
- 不正 Shift-JIS / 不正モードは書込みなしとする。

### 6.4 Unifont の代替

Unifont は 16 行のみである。可変幅は DEV 出力（32 bytes 固定）で区別できない。
主候補は東雲であり、Unicode 経路は Unifont 採用時のみに用いる。

## 7. ROM 配置案

### 7.1 配置（段階収録の例）

| 銀行 | 内容 | 備考 |
|---|---|---|
| 先頭バンク | 既存の生成テーブル・スタブ・上書き・起動・ベクタ | 変更なし。対象スロットは実装時に対象外から対象候補へ移る設計である |
| bank1–bank2 | 索引テーブル | 3,000 字で 12,000 bytes は 2 バンクで収まる。1 バンクでは収まらない |
| bank3 以降 | グリフデータ | 16×16 領域と 12×12 領域を別々に置く。バンク境界を跨ぐグリフを禁止 |

索引は 2 サイズで共通の単一テーブルである。グリフオフセットは
`ID × 32`（16×16）と `ID × 24`（12×12）で計算するが、12×12 は
§3.3 のバンク補正を用いる。別々の索引は持たせない。

### 7.2 バンク切替と MPR 復元

- 呼出時の窓配置は既存の銀行配置で固定する。フォント訪問は別窓を
  用い、切替前後で保存・復元する。
- 第 6 番目の窓を優先し、バッファ最上位バイトがフォント窓と重なる場合は
  第 3 番目の窓へ切り替える。窓の変更は割り込み時の態度に影響しうるため、
  DEV 契約では割り込み時の窓状態を保存・復元する。
- スタックの使用は戻り先と切替用に限定し、スタック境界で割れないこと。
- MPR/SP の保存・復元は実際の DEV callee が存在する段階では検証できない。
  本節の要求は契約として確定するが、実装検証は `NOT_RUN` とする。
  ホストモデルでトートロジーな保存確認をしてはならず、純正の保存規約は
  `UNKNOWN` のまま維持する。実コアでの窓切替と範囲拒否は #708 の
  受入条件へ引き継ぐ。
- ビルド検証は現行で bank1–31 を埋め値とする。後継では bank1 以降に
  フォントを含む構成へ変更し、検証ロジックも更新が必要である。
  フォントデータは禁止拡張子のまま格納するとガードで拒否されるため、
  変換器で生成するソース生成表として取り込む設計とし、バイナリの直格納はしない。

## 8. 合成テスト設計（著作権上問題のない独自模様のみ）

### 8.1 合成 BDF 仕様

完全自作の少数文字の合成 BDF で検証する。純正フォントや商用媒体は使わない。
合成 BDF は §5 の検証規則を満たす最小のファイルである。

- 収録文字は重複のない複数の `ENCODING` とする（ソート順で ID が決まる）。
  最小・最大 ID の境界を含む。
- 各文字の `BBX`/`DWIDTH` がセル全体であり、`BITMAP` の行数・行長が
  正しい。行ビットは MSB 左端である。
- 12×12 の行は下位 4 ビットがゼロである。
- 16×16 の行は 16 ビットすべてが有効である。
- 入力順序を変えても生成結果は同一であること（ソートで保証）。

合成グリフの例（独自データ）:

- 空白: 全ゼロ。
- 左端: 毎行 `F0 00`（上位 4 画素のみ）。
- 位置識別: 行ごとに `80 00` / `40 00` / `20 00` / `10 00` を循環。
- 順序: 行が決定的式で変化する。
- 先頭・末端のみ非ゼロ。

これらは固定された公開配布ファイルの抽出ではない。

### 8.2 区分 A：実装済みモデルに対する PASS

ホストモデルで実際に実行し、期待値と照合する。実コアの実行ではない。

| ID | 検証 | 入力 | 期待 |
|---|---|---|---|
| POS-STORE12 | 12×12 の 24 バイト格納 | 合成 BDF の 12×12 変換 | 24 bytes は合成行の正規化と一致する |
| POS-OUT12 | 12×12 の 32 バイト RAM 出力 | POS-STORE12 の 24 bytes + 呼出 | 32 bytes は 24 bytes + 末尾 8 bytes ゼロと一致する |
| POS-OUT12Z | 12×12 の末尾 8 バイトゼロ埋め | POS-OUT12 | 末尾 8 bytes はすべてゼロである |
| POS-OUT16 | 16×16 の 32 バイト格納・出力 | 合成 BDF の 16×16 変換 | 32 bytes は合成行と一致する |
| POS-INDEX | 文字索引の正しい検索 | 合成 ID の文字コード | 共有の二分探索が正しい ID を返す |
| POS-ID-BOUND | 最小・最大グリフ ID | 先頭・末尾の合成文字 | 正しい ID・バンク・オフセットを返す |
| POS-BANK | ROM バンク境界 | バンク境界付近の ID | バンク補正により正しい銀行・オフセットを返す |
| POS-REGEN | 再生成一致 | 同一合成入力の 2 回変換 | バイト一致する |

負例（区分 A の一部）:

| ID | 検証 | 入力 | 期待 |
|---|---|---|---|
| NEG-SJIS | 不正 Shift-JIS | 範囲外の先頭・第2 | 書込みなし。エラー戻り値を純正値として固定しない |
| NEG-UNMAP | 未収録文字 | 索引にない文字 | 同じ二分探索が `UNMAPPED` を明示し、別の ID を返さず、グリフデータを返さない |
| NEG-ROWLEN | 不正 BDF 行長 | 行長が正しくない行 | 変換器が拒否する |
| NEG-DUP | 重複 ENCODING | 同一の値が 2 回 | 変換器が拒否する |
| NEG-BBX | 不正 BBX | セル全体でないグリフ | 変換器が拒否する |
| NEG-BOUND | グリフ ID の境界 | `id<0`、`id>=count`、割当超過 | 上位関数が拒否し、最小 ID と最大有効 ID を受理する。バンク内オフセット＋長が 8KiB 以内に収まる |
| NEG-RAM | 宛先 RAM 範囲外 | RAM 外の宛先 | 書込みなし |
| NEG-SIZE | 宛先が 32 バイト未確保 | 不足する宛先領域 | 書込みなし（境界試験） |
| NEG-RAM-RANGE | RAM 範囲不足 | 短い範囲への呼出 | 書込みなし |
| NEG-BANKSPAN | ROM バンク跨ぎ誤計算 | バンク境界を跨ぐと誤計算する ID | 正しいバンク補正でなければ拒否。無補正の計算は不合格 |

MPR/SP の実装検証は本区分に含めない。ホストモデルでトートロジーな
保存確認を行わない。

### 8.3 区分 B：契約として確定したが実装未検証（NOT_RUN）

- 実際の DEV callee による 32 バイト RAM 書込み
- 実際の MPR 保存・復元
- 実際の SP 保存・復元
- 実コア上での窓切替
- 実コア上での RAM 境界拒否
- 実コア上での無書込み保証

いずれも `NOT_RUN` とする。ホストモデル成功を実コア成功に昇格させない。

### 8.4 区分 C：純正互換性として未確定（UNKNOWN）

- 純正フォントの字形
- 純正の 12×12 出力長
- 純正の bit 順・行順
- 純正の MPR/SP 保存規約
- 純正の戻り値・エラー

いずれも `UNKNOWN` とする。合成テストの合否は純正互換の証拠ではない。

## 9. #708 の最小実装範囲と開始条件

### 9.1 今すぐ準備できるもの

- 合成 BDF 仕様（§8.1）
- 決定的変換器の設計（§5）
- 文字索引（§4.4）
- ROM 容量計算（§3）
- バンク配置モデル（§7）
- Host 正例・負例テスト（§8.2–§8.3、ホストモデル）
- DEV 専用 32 バイト出力契約（§6）

合成フォントによる変換器・ホストテストは Owner 承認なしで準備できる。
必要なら合成フォント変換器のみを別子 Issue へ分割する。

### 9.2 Owner 承認が必要なもの

- 実フォントの採用
- 実フォント本体からの生成物の配布
- ROM への実フォント格納
- `build_rom.py` の ROM 資産配置変更
- 実際のスロット配線
- DEV 実装
- MPR を変更する実コア試験

現行の着手ゲートを承認なしに解除しない。承認が得られるまで、
フォントの取り込み・ROM 配線・使用はしない。未承認は `PENDING` のままである。

### 9.3 推奨と残存 UNKNOWN

- フォント: 東雲 Gothic Medium Regular の 12/16 固定長（監査文書が
  SHA を固定）。Unifont は主候補から外す。
- ライセンス: 東雲は `CONDITIONAL` であり、Owner 承認前は確定しない。
  MIT との関係は本リポジトリの MIT LICENSE は自ら所有または許諾を受けた部分に
  のみ適用されることを明確にし、フォント部分は別文とする。
- 変換: §4–§5 の算術＋ソート索引。
- 出力: 2 bytes/行、上から下、MSB 左端、12×12 は末尾 8 bytes ゼロの 32 bytes。
- 配置: §7（bank1–bank2 索引、bank3 以降グリフ、窓切替）。
- 最小範囲: Owner が選定する数千字の部分集合から始め、両サイズの
  変換器と実コア試験を先に固める。最初の実装単位はホスト変換器→
  host モデル→ROM 格納と検証更新→最小実装（正例のみ）→負例拡張の順序である。
- 純正のビット順・行順・パディング・戻り値・保存は UNKNOWN のままである。
  DEV 契約はこの UNKNOWN をデザインで置き換えるものであり、System Card 互換の
  主張ではない。
