### 1.2 再評価で分かったこと

1. **観測した 1 例（MPR1=$FF）の根本原因は「スタックページ（`$2100〜$21FF`、MPR1）が $FF（I/O）を指していること」である。** push の書込みも pop の読出しも、同じ原因から副作用を起こす。#470 は書込み側（push）を、#481 は JSR の push を、それぞれ別の入口で見たに過ぎない。
2. **push 側だけを守る方式は、pop 側の読出し副作用を残す（O3）。** これは #470 が既に示した。
3. **呼出し側ガード（JSR の後で MPR1 を検査する）は、JSR 自身の push を守れない（O6）。** JSR・PHA は命令自身が積むので、命令の外にある検査では間に合わない。PHP・BSR・割込み入口も同じ構造と考えられるが、これらで I/O に着地した観測は無い（PHP は VDC の変化なしとだけ記録）。
4. **#470 の probe は MPR1 を `SetMpr` で直接設定している**（`geargrafx_block_write_guard.cpp` の `memory->SetMpr`）。ゲスト命令の TAM を経由していない。#481 は ROM 内の TAM で MPR1 を設定している。方式 A を TAM の実行時に効かせる場合、#470 の probe のままでは「TAM を通らない設定」を検査できない。この差は後述の分割案で扱う。
5. 本書の観測は 1 バイト転送、MPR1=$FF の 1 例のみである。他の長さ、他のバンク（ROM、BRAM など）、NMI、実機のタイミングは未検証。

## 2. pinned コアのソース読み（【ソース読み】。実行による確認ではない）

引用元はすべて pinned Geargrafx b49ae82 の `src/` 内。行番号は読んだ時点のもの。`-debugger` 側の `src/` とは差分が無いことを `diff -rq` で確認した（`.o` を除く）。

### 2.1 push / pop は共通関数を通る

| 関数（ファイル） | 内容 |
|---|---|
| `StackPush8` / `StackPush16` / `StackPop8` / `StackPop16`（`huc6280_inline.h` 371〜399 行） | すべて `m_memory->Write` / `m_memory->Read(STACK_ADDR \| m_S)` を呼ぶ。`STACK_ADDR` は 0x2100（`huc6280.h` 44 行。`GG_TESTING` のときだけ 0x0100） |
| 順序（push） | 書込み → `S` を減らす。`StackPush16` は上位バイト、下位バイトの順に 2 回書く |
| 順序（pop） | **`S` を増やす → 読出し。** 読出しの前に `S` が動く |

`STACK_ADDR` を使う箇所は上の 4 関数だけである（ソース全体の grep）。`S` を直接変える箇所は `TXS`（`huc6280_opcodes.cpp` 968 行）と reset（`huc6280.cpp` 220・228 行）だけで、この読みでは他に見つからなかった。

要求された確認対象の呼出し元：

| 対象 | 呼出し元（ファイル：行） | 共通関数 |
|---|---|---|
| JSR | `OPCode0x20`（`huc6280_opcodes.cpp` 219〜224 行。オペランド取得後に `StackPush16(pc - 1)`） | `StackPush16` |
| PHA | `OPCode0x48`（同 470〜473 行） | `StackPush8` |
| PHP | `OPCode0x08`（同 74〜77 行。B フラグを立てて push） | `StackPush8` |
| BSR | `OPCodes_Subroutine`（`huc6280_opcodes_inline.h` 198〜204 行） | `StackPush16` |
| RTS | `OPCode0x60`（`huc6280_opcodes.cpp` 611〜614 行） | `StackPop16` |
| RTI | `OPCode0x40`（同 418〜422 行。P を pop してから PC を pop） | `StackPop8`、`StackPop16` |
| IRQ 入口 | `HandleIRQ`（`huc6280_inline.h` 98〜132 行。115 行で `StackPush16(pc)`、116 行で `StackPush8(P & ~B)`） | `StackPush16`、`StackPush8` |
| TransferStart | `OPCodes_TransferStart`（`huc6280_opcodes_inline.h` 668〜674 行。Y、A、X の順に push） | `StackPush8` ×3 |

### 2.2 RunInstruction の順序と、IRQ の受理位置（C-2 の根拠）

`HuC6280::RunInstruction`（`huc6280_inline.h` 56〜96 行）の順序：

1. `Fetch8()` で opcode を取る（76 行）。**PC はここで進む。**
2. `CheckIRQs()`（79 行）。実体は `m_irq_pending = I フラグが立っていれば 0、そうでなければ IRR & ~IDR`（136 行）。**IRQ の保留は命令の実行前の I フラグ・IRR で決まる。**
3. `m_opcodes[opcode](this)` で命令を実行する（81 行）。TAM はここで `Memory::SetMprTAM` を呼び、`m_mpr[i] = value` を代入する（`huc6280_opcodes_inline.h` 444〜448 行、`memory.cpp` 298〜323 行）。
4. 90 行：`(m_irq_pending || IRR のビット 2) && m_transfer_state == 0` なら、**同じ `RunInstruction` の中で** 91 行の `HandleIRQ()` を呼ぶ。`HandleIRQ` は 115〜116 行で PC と P を push する（`I` フラグの再検査は無い）。

**ソース読みの結論：IRQ が保留中（実行前に I=0 かつ IRR 非マスク）の状態で `TAM`（MPR1 を $FF にする）を実行すると、TAM が MPR1 を変えた直後、同じ `RunInstruction` の 91 行で `HandleIRQ` が `STACK_ADDR | S`（= `$21xx`）へ 2 回書く。この書込みは `Memory::Write`（`memory_inline.h` 265〜）が `m_mpr[1] == 0xFF` を見て Hardware Page に回し、`offset & 0x1C00 == 0` の番地は `HuC6270::WriteRegister` へ届く（同 295〜304 行）。** つまり、1 命令ずつ進めて「命令の後に MPR を比較する」ハーネスは、この push を止められない。この順序は**ソース上は実在する**。ただし実コアで測っていないので、効果の大きさ（VDC のどのレジスタがどう変わるか）は UNMEASURED。

補足（ソース読み）：

- `m_irq_pending` は 79 行の `CheckIRQs` でしか決まらない。TAM 自身の実行中に新しく立った IRQ（`InjectCycles` 経由のハードウェア進行など）は、`HandleIRQ` の分岐条件（`m_irq_pending` のビットを見る）を満たさない。タイマ（IRR のビット 2）は 90 行の条件に含まれるが、`HandleIRQ` の中でも `m_irq_pending` のビット 2 を要求する（103〜104 行相当）。**よって、問題になるのは TAM の実行前から保留していた IRQ である。** この読みも実測していない。
- 同じ理由で、TAM と同じ命令の中の I フラグ操作は効かない。I フラグが効くのは**次の命令の** `CheckIRQs` からである（`SEI` を TAM の前に実行済みであることが要る）。
- `m_transfer_state != 0` の間は 90 行で IRQ が受理されない。転送の最後の 1 バイトの後も、`TransferEnd`（状態 0 に戻す。687 行）を実行する `RunInstruction` の 91 行で IRQ が受理されうる。これは O9 の観測と矛盾しない。
- デバッガの memory breakpoint（`Memory::Write` 277〜278 行の `CheckMemoryHooks`）は書込みの**前**に呼ばれるが、止まるのは `RunInstruction` が戻った後（`geargrafx_core_inline.h` 101 行付近）である。#470 の「write breakpoint は副作用後にしか止まらない」と整合する。

## 3. 方式の定義と、推奨する検証順（開発側の提案）

| 方式 | 定義 | 検査する時点 |
|---|---|---|
| A | スタックページ（MPR1）が許可バンクでない状態を**事前に拒否**する（危険な MPR1 マッピングの事前拒否）。許可バンクは WRAM（$F8）のみとする | MPR1 を変える操作（TAM）の時点、または JSR / 転送などの入口の前 |
| B | TransferStart の push と TransferEnd の pop を保護する | TransferStart から TransferEnd まで |
| C | スタックへのアクセス（push・pop）が起きる**直前に**、各スタックアクセスの副作用の前で実行を止める | 各スタックアクセスの直前 |

「拒否」「止める」は、ハーネスが実行を打ち切ることを指す。ゲストの命令の意味を変えて続行することではない。

**推奨する検証順（開発側の提案。オーナー承認ではない）：**

1. 方式 A の実コア検証（IRQ 保留中の TAM の負例を含む。第 8 節）。
2. 方式 C を A の補完として評価する（第 9 節の条件）。
3. A と C の併用の検証。

**B は単独候補から外す。** B は TransferStart / TransferEnd にしか効かず、JSR・PHA・PHP・BSR・割込み入口を覆えない（#473 の目的を満たさない）。B の pop 前フックは、C の「スタックアクセス前に止める」に含まれる部分集合として扱う。B' のように pop を抑止して続行する案は、ゲストの命令の意味を変えるため提案しない。

## 4. 方式 A：MPR1 の危険マッピングを事前拒否

| 観点 | 評価 |
|---|---|
| 安全性（範囲） | **MPR1 が $FF にならない限り**、push・pop・JSR・BSR・割込み入口・RTS・RTI・TransferStart/End のスタックアクセスは I/O に届かない（$FF 以外の危険バンクは別）。ただし「ならない」ことを検査が保証できる経路に限る。実測は $FF の 1 例のみ |
| TransferEnd の pop | 覆える見込み。TransferStart の前に拒否すれば push を書かない。転送の途中では IRQ が受理されなかった（O9、コアの挙動。実機は未確認）。転送中に MPR1 が変わるかどうかは測っていない |
| JSR | 覆える見込み。JSR の push より前に拒否する。ガードを JSR の後に置く方式（O6）と違い、命令自身の push が I/O に届かない |
| 実装箇所（案） | (a) **ステップ実行ハーネス**：無改造コアを 1 命令ずつ進め、各命令の実行前に全 MPR を検査する（既存の参照ガードと同じ手法、O11）。(b) 検証専用コアパッチで TAM の直前に検査する案。(c) 呼出し側契約：API 入口の前に MPR1 が RAM であること（検出のみ、O6） |
| **(a) の穴（C-2）** | **IRQ が保留中の TAM ステップでは、TAM が MPR1 を $FF にした直後、同じ `RunInstruction` の中で割込み入口の push が I/O に届きうる**（第 2.2 節、ソース読み）。命令の後に MPR1 を検査しても、この push は止められない。実コアでは未測定（**UNMEASURED**）。必須の負例は第 8 節。対策案は、(i) TAM の実行前に、次の命令が TAM かつ書込み値が許可バンクでないかをハーネスが先読みして拒否する、(ii) TAM の前に I フラグを立て（または IRR / IDR をマスクして）IRQ を保留させない、(iii) C を併用する。いずれも未検証 |
| 弱点 | (1) free-running の実行や、TAM 前フックだけでは、TAM 以外の設定（リセット直後の初期値、ハーネスの直接設定）を検査できない。リセット直後の MPR0〜6 は既定で 0 以外の乱数（第 2.3 節）で、$FF になりうる。(2) 正規のゲームが MPR1 を一時的に I/O にする使い方を拒否する可能性があるが、本プロジェクトの用途（合成 ROM、DEV ROM）では対象外。(3) $FF 以外の危険なバンク（ROM、BRAM、CD RAM など）の扱いは未検証。許可バンクを WRAM のみにすれば安全側だが、過剰拒否になりうる |
| 未検証の副作用 | TAM を拒否した後の CPU 状態（PC、S、P、MPR）の扱い。TAM を連続して実行する場合の途中状態 |
| テスト可能性 | 高い。#481 の CASE_IO（ROM 内の TAM で MPR1=$FF）が負例になる。MPR1=$FF 負例を保持する |

## 5. 方式 B：単独候補から外す（参考として残す評価）

| 観点 | 評価 |
|---|---|
| 範囲 | **TransferStart / TransferEnd に限られる。** JSR、PHA、PHP、BSR、割込み入口は対象外。#473 の目的（JSR のスタック操作を守る）を満たさない |
| 扱い | 単独では提案しない。必要な部分（TransferEnd の pop 前）は、C のスタックアクセス前の停止に含める |
| 参考：pop 前フックの要点 | pop 側に止める仕組みが無いと O3 の副作用が残る。pop を抑止して続行する案（B'）は、状態は保てるが転送本体を止めない（O4）ため、別途 #367 の宛先ガードが要る。ゲストの命令の意味も変わるので提案しない |

## 6. 方式 C：各スタックアクセスの副作用の前に止める

| 観点 | 評価 |
|---|---|
| 安全性（範囲） | スタックアクセスは 4 関数に集約されている（第 2.1 節、ソース読み）。そこに置けば、JSR・PHA・PHP・BSR・割込み入口・RTS・RTI・TransferStart/End を一箇所で覆える見込み。MPR1 がどう設定されたかに依存しない（TAM でも直接設定でも検出できる）。**IRQ 保留中の TAM ステップでも、`HandleIRQ` の push（`StackPush16`）の前で止められる見込み**（A の穴を補う）。いずれも未測定 |
| 実装箇所（案） | **検証専用コアパッチ**：4 関数の書込み前・読出し前のフック。#470 のパッチは TransferStart の push に既にフックを付けている。本番機構ではなく、**検証コアのパッチと製品実装は分ける**（第 12 節） |

## 8. 方式 A の穴：IRQ 保留中の TAM（C-2）と必須の負例

**穴の内容：** TAM が MPR1 を I/O バンクにするステップの中で、保留中の IRQ が同じ `RunInstruction` で受理されうる（第 2.2 節、ソース読み）。そのため、命令の後に MPR1 を検査する方式 A(a) では、割込み入口の push を止められない。**この穴は、実コアで測るまで UNMEASURED であり、A が覆うとは言わない。**

**必須の負例（N-IRQ-TAM。方式 A の実コア検証に含める。未実施）：**

| 項目 | 内容 |
|---|---|
| 前提 | 合成 HuCARD、無改造 pinned コア、1 命令ずつの実行。MPR1=$F8、スタックは WRAM。VDC の AR、R0、R[7]、ステータス（`$05`）、読出しバッファ（`0xBEEF`）に既知の値を置く |
| 状態 | TAM の実行前に、I フラグが 0、IRQ1 が IDR でマスクされていない、IRQ1 が assert 済み（IRR のビット 1）。A は $FF |
| 操作 | `TAM #$02`（MPR1 ← $FF）を 1 ステップ実行する |
| 観測 1 | ハーネスは TAM の**前に**拒否できたか（TAM が実行された場合は、その事実を記録する） |
| 観測 2 | IRQ 受理の stack 書込み（`$21xx`、bank $FF）が発行されたか。発行された回数と番地 |
| 観測 3 | VDC の状態（AR、R0、R[7]、ステータス、読出しバッファ）が変わったか |
| 観測 4 | CPU レジスタ（A/X/Y/P/S/PC）と MPR0〜7 が拒否前の値のまま保たれたか。IRQ の保留状態（IRR、IDR、`m_irq_pending` 相当）はどうなったか |
| 対照 | (i) 同じ条件で拒否しない対照（副作用の再現。試験の感度）、(ii) I フラグを 1 にして保留させない場合、(iii) IRQ が無い場合（TAM 単独）、(iv) TAM の前に先読みで拒否する案、(v) C の停止点を併用する案 |

TAM の実行中に新たに立った IRQ が受理されるかどうかも、ソース読み（第 2.2 節の補足）では受理されない見込みだが、実測していない（UNMEASURED）。

## 9. 方式 C の条件（C-3）

### 9.1 確認が要る対象

JSR、PHA、PHP、BSR、RTS、RTI、IRQ 入口、TransferStart、TransferEnd。第 2.1 節のとおり、すべて同じ 4 関数（`StackPush8/16`、`StackPop8/16`）を通る（ソース読み）。ただし、これは「共通関数がある」という読みであり、各命令で実際に止まること・止めた後の状態は**すべて UNMEASURED**。

### 9.2 命令の途中で止めたときに残りうる副作用（ソース読み。実測していない）

| 項目 | 停止点で残りうること |
|---|---|
| PC | `RunInstruction` は opcode の取得（76 行）で PC を進める。JSR はオペランド取得後（`AbsoluteAddressing`）に push するので、**PC は命令の後ろ（opcode とオペランドの分）に進んだまま**止まる。TransferStart は push の後に `Fetch16` ×3 をするので、push の前で止まれば PC は opcode の後。TransferEnd の PC 補正（`+ 6`、691 行）は pop の後なので、pop の前で止まれば未適用。IRQ 入口の前で止まる場合、命令自体は完了しており、PC は次の命令 |
| A / X / Y | push の前で止まれば変化しない。pop は `SetValue(StackPop8())` の形で、pop の前で止まれば代入されない（TransferEnd の X、A、Y） |
| P | PHP / IRQ 入口の push の前で止まれば変化しない。IRQ 入口では I フラグを立てる前（117 行）、RTI / PLP では `SetP` の前で止まる。TransferStart は push の前に `m_transfer_state = 2`（670 行）を立てるので、push の前で止めても**状態変数 `m_transfer_state` は 2 のまま** |
| S | push は「書込み → S を減らす」なので、書込みの前で止まれば不変。**pop は「S を増やす → 読出し」なので、読出しの前で止めても S は 1 つ（RTS / RTI / TransferEnd では複数）増えている。** 停止点を `S` を動かす前にするか後にするかで結果が変わる |
| MPR | スタックアクセスの停止では変化しない。TAM が先に実行されていれば、TAM による MPR は反映済み（第 8 節） |
| VDC | 読出し・書込みの前で止まれば変化しない。`InjectCycles` による VDC の時間進行（`Memory::Read/Write` の中、ハードウェア側のクロック）は、止めた分だけ進まない。サイクル計上（`m_cycles`）とクロックの差が出る |
| WRAM | `StackPush16` は上位バイト、下位バイトの 2 回書く。MPR1 は固定なので通常は 1 回目の前で止まるが、1 回目で止めない設計だと 1 バイトだけ書かれた状態が残る |
| 宛先データ | TransferStart の push の前で止まれば転送本体は始まらない（宛先は不変）。**TransferEnd の pop の前で止める場合は、転送本体が既に実行されており、宛先は書込み済み**（O4 と同じ構造） |
| IRQ 保留状態 | `m_irq_pending` は `CheckIRQs`（79 行）の結果として既に決まっている。IRR / IDR は止めただけでは変わらない。IRQ 入口の push の前で止めると、IRQ は未受理のまま、保留として残る（次の `CheckIRQs` で再計算される） |

打ち切ったあとの状態をゲストの命令境界に戻す（巻き戻す）のか、**打ち切ってゲストの実行を終了する**のかで、残ってよい副作用の定義が変わる。本書の提案は後者（実行を打ち切り、危険な状態でゲストを続行しない。第 12 節）。

### 12.2 推奨案（開発側の提案。オーナー承認ではない）

- **方式 A を先に実コアで検証し、C を補完として評価する。** B は単独候補にしない。

- 拒否したら、**ゲストの実行を打ち切る。** 危険な状態のまま続行しない。
- **検証コアのパッチと製品実装は分ける。** 検証用のフック・ハーネスは本番に入れない（#473 コメント 1 の前提「コア改造は検証専用」と整合）。

### 12.3 理由

- A は範囲が広く、既存の参照ガードの手法（ステップ実行、O11）を流用できる見込みがある。ただし IRQ 保留中の TAM に穴がある可能性があり（第 8 節）、そこは C が補える見込み。
- B は JSR を覆えない（第 5 節）。
- 呼出し側契約（#473 コメント 3）は、入口ガードだけでは JSR の push を守れない（O6）という限界を、契約として扱う方針である。A / C は、その契約が破れたときの副作用を**検証側で**確かめるためのもの。

### 12.4 代替案

- A のみ（C は使わない）：コアパッチが要らないが、IRQ 保留中の TAM が穴として残りうる。対策案 (i)(ii) を検証して覆えるなら成立しうる。
- C のみ：MPR1 の設定経路に依存しないが、検証専用パッチが大きく、回帰リスクが高い。
- A + C の併用：最も広いが、実装・検証の量が最大。
- 呼出し側契約のみ（#473 コメント 3）：副作用は防げない（検出のみ）。
- 許可バンクを WRAM 以外にも広げる：過剰拒否は減るが、根拠となる実測が要る。
