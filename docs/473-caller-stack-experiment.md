# #473 呼出し側スタック契約の合成実験

## 位置づけ

- オーナー判断（#473 の Phase B）：API を JSR する時点で、呼出し側が有効な RAM スタックを保証する。
- 本書は、その契約の前提を合成 ROM と無改造の Geargrafx コア（b49ae82）で観測した結果である。**本番の安全ゲートではない。** #459 / #367 のゲートは解除しない。本番の安全機構への適用は行わない。
- 対象の ROM はテスト専用の 8 KiB HuCARD（`tests/fixtures/caller_stack_contract.s`）。参照 BIOS 由来の内容は含まない。
- 実行：`tests/integration/geargrafx_caller_stack_contract.py`（Linux、TOOLS_DIR 指定）。コアやツールが無い場合は FAIL（終了コード 1）で、スキップしない。

## 方法

- ca65 / ld65 で 3 種類のビルドを作る（`CASE_RAM`、`CASE_IO`、`CASE_IRQ`）。
- 探針 `tests/integration/geargrafx_caller_stack_probe.cpp` は無改造コアを使う。
  - `HuC6280::RunInstruction` で 1 命令ずつ進める。TII は 1 バイトずつ進む（TII の状態機械）。
  - 記録：ラベル到達（TRACE、HITS）、WRAM の書込み（WRW）、VDC 登録の**変化**（VDW、旧値と新値）、転送（XFER）、IRQ 線（IRQ）。
- ステップ番号は RunInstruction の呼出し回数。

## 観測範囲（何を見て、何を見ていないか）

| 区分 | 観測したもの | 観測していないもの |
|---|---|---|
| CPU | ラベル到達時の A/X/Y/P/S/MPR（TRACE）、ラベル到達回数（HITS） | 任意の命令ごとの CPU 状態 |
| WRAM | 書込みの番地・旧値・新値（WRW） | 読出し |
| VDC 書込み | 登録値の**変化**（VDW）。登録（R0、AR、R17 等）、ステップ、PC、旧値、新値。**バス書込みの完全な記録ではない** | 値が変わらない書込み（変化のみ記録するため見えない） |
| VDC 読出し | 観測していない | データポート読出し、ステータス読出しによる副作用（SR のクリア、読出しバッファ） |
| I/O 読出し | 観測していない | スタックページが I/O に当たった時の読出し値（RTS や RTI が pop する値を含む） |
| 割込み | IRQ 線の assert/deassert と、ベクタ分岐（IRQ、TRACE の `irq1_entry`） | NMI（pinned コアに受理経路が無い） |

## 判定と負例

- 契約を満たす場合の許可 WRAM 書込みは、`$01FC〜$01FF` と `$0210` だけ（`ALLOWED_RAM_WRITES`）。それ以外の WRAM 書込みは FAIL。
- 呼出し側 SP = $FF を検査する（`caller_precondition_sp`）。
- VDC の検査は、JSR の戻りアドレス（R0 = JSR の PC+2、JSR と同じステップ）と、PHA の値（AR = A、api_guard の次のステップ）を、ステップ・PC・値で照合する。無関係な VDC 変化だけでは PASS しない。
- 判定の負例は実コアより先に実行する（`selftest`）。無関係な VDC 変化、誤った R0 の値、$0100 への書込み、呼出し側 SP=$FE は、判定が棄却しなければならない。
- 実コアの負例 `ram_inject_negative`：契約を満たす構成に、$0100 への注入書込みを 1 回加えたビルド。`stack_writes_in_wram` で FAIL することが期待値で、その通り棄却された。

## 結果 1：契約を満たす場合（MPR1 = RAM $F8）

| 項目 | JSR 直前 | RTS 後（post_return） | 判定 |
|---|---|---|---|
| A | $11 | $11 | 一致 |
| X | $22 | $22 | 一致 |
| Y | $33 | $33 | 一致 |
| P（B を除く、マスク $EF） | $4D | $4D | 一致 |
| S | $FF | $FF | 一致 |
| MPR0〜7 | `[$F8, $F8, $58, $31, $26, $3E, $63, $00]` | 同じ | 一致 |
| ガードが読んだ MPR1 | $F8（ステップ 16 の A） | - | RAM として許可 |
| ガードのフラグ（WRAM $0210） | - | 1 | 許可を検出 |
| RTS の実行 | ステップ 23（`guard_rts`） | - | 観測 |
| post_return の到達 | ステップ 24（RTS の直後の命令） | - | 観測 |
| VDC 書込み（VDW） | 0 件 | - | 観測 |
| WRAM の書込み | $01FC〜$01FF と $0210 のみ | - | 観測 |

WRW の記録：ステップ 12 で $01FE = $15、$01FF = $E0（JSR が積んだ戻りアドレス）。ステップ 13 で $01FD（P）、ステップ 14 で $01FC（A = $11）。

## 結果 2：契約を破る場合（JSR 前に MPR1 = $FF）

### 観測（実コアの記録）

| ステップ | 観測 | 種別 |
|---|---|---|
| 14 | VDC R0（MAWR）が $0000 → $E019（VDW） | 観測 |
| 15 | PHP の実行。VDC の登録変化は無し | 観測（書込みの有無は不明。変化が無かったのみ） |
| 16 | VDC AR が $0000 → $11（VDW）。PHA の A = $11 | 観測 |
| 18 | ガードが読んだ A = $FF（MPR1 = $FF を検出、フラグは 0） | 観測 |
| 24 | `guard_rts` のラベルを実行（HITS に 1 回） | 観測 |
| 25、28 | VDC R17 が $0000 → $02、$02 → $03（VDW。PC は $0000、$0001） | 観測（書込み元は未特定） |
| 26 以降 | `irq1_entry`（$E039、`rti`）のラベルを 18 回到達 | 観測 |
| 80 | 80 ステップで停止（`post_return` は一度も到達せず） | 観測 |

- WRAM の書込み（スタック範囲 $01FC〜$01FF）は、ガードの窓の中で 0 件。スタックは I/O に当たった。
- `post_return` のラベルは到達していない（HITS に無し）。
- `irq1_entry` は、`guard_rts`（$E038）の直後のアドレス（$E039）である。違反ケースで $E039 に到達したのは RTS の後の実行であり、IRQ の受理ではない。

### 推定（観測の解釈。直接の証拠ではない）

- ステップ 14 の R0 の変化（$E019）は、JSR が積む戻りアドレス（JSR の末尾の PC-1）と同じ値である。VDC データポートへの書込みが R0 を変えたと推定する。
- ステップ 16 の AR の変化（$11）は、PHA が $21FC（I/O）へ書いた結果と推定する。
- 上の推定は、コアの I/O デコードに基づく。書込みの番地は直接は観測していない。

### 判定

- **ガードは違反を検出した**（ステップ 18 の A = $FF、フラグ 0）。
- **違反時の副作用は防がれなかった**。JSR の戻りアドレスの書込みと、ガード自身の PHA の書込みは、既に I/O に当たっていた（VDW で観測）。入口ガードは違反の検出に限られる。
- **post_return 未到達は観測した事実**。
- **RTS の戻り先は未特定**。RTS が pop した値は、I/O 上の読出しに由来する。その読出しは観測していない。したがって、RTS が何番地に戻ったかは判定できない。$E039 への到達は観測したが、RTS から $E039 への経路（$0000、$0001 付近の実行を経由したかどうか）は確定していない。
- 実行は 80 ステップで止まった。この停止は、違反の後の制御が不定であることの観測であり、契約違反時の振る舞いの保証ではない。

## 結果 3：IRQ1 と TII（8 バイト、ROM → WRAM $0220）

| ステップ | 観測 |
|---|---|
| 9 | TII の開始（PC は TII のまま。ラベル `tii_start`） |
| 9〜17 | 1 ステップに 1 バイトずつ転送（WRW：$0220〜$0227）。XFER は `completed: false`。PC は TII のまま |
| 11 | IRQ1 の線を assert（IRQ の記録）。転送の途中（2 バイト目の後） |
| 18 | 最後のバイトの書込みで転送が完了（XFER `completed: true`）。**同じ RunInstruction の呼出しの中で IRQ1 ベクタへ分岐**し、PC が `irq1_entry`（$E039）になった |
| 19 | `irq1_entry` のラベルを最初の命令境界で記録（TRACE）。IRQ の線は入口で deassert |

- ステップ 9 の WRW に、WRAM $01FD〜$01FF の 3 件（値 $FF、$F8、$4B）がある。TII の転送先（$0220〜）とは別の書込みで、由来は未確認（起動直後の状態として記録されたものと推定するが、検証していない）。
- 転送の途中（ステップ 9〜17）では IRQ を受理しなかった（PC は TII のまま）。
- IRQ1 のベクタ分岐は、**最後の転送ステップ（ステップ 18）の中で起きた**。ステップ 19 は、その分岐の後の最初の命令境界の記録である。
- 転送後の $0220〜$0227 は A1〜A8 で、期待値と一致した。
- 根拠のソース：`huc6280_inline.h:90` の `if((m_irq_pending || ...) && (m_transfer_state == 0)) HandleIRQ();`。転送の途中では受理されず、転送完了の直後に受理された。この観測は、その行の予測と一致する。
- 注意：この挙動は合成コアのものである。実機のタイミングは未確認。

## 未検証・限界

- 実機の TMA・IRQ・NMI の挙動は未確認。pinned コアに NMI の受理経路は無いため、NMI は対象外（#473 の受入 7 のまま、オーナー確認が必要）。
- VDC の読出し、I/O 読出しの副作用（SR のクリア、読出しバッファ）は観測していない。VDW は変化のみを記録するため、値が変わらない書込みは観測できない。
- 契約違反は MPR1 = $FF の 1 例だけを試した。S 不足、T=1 などの他の違反は未実験。
- RAM とみなすのは WRAM バンク $F8 のみ。
- 1 回目のステップだけ `RunToVBlank` を使い、以後は `RunInstruction` を使う（コアのハードウェアクロック設定のため）。VDC のタイミングは CPU 状態の観測に影響しない想定だが、本実験では検証していない。
- JSR 直前の P と MPR2〜7 は、判定に絶対値を使っていない（前後の一致で判定）。

## 再現

```
TOOLS_DIR=<tools> python3 tests/integration/geargrafx_caller_stack_contract.py --out <dir>
```

`<dir>/caller-stack-evidence.json` に、各ケースの TRACE、WRW、VDW、XFER、IRQ、HITS、END を出力する。
