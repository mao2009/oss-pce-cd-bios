# Issue #90: slot `$50`（候補 `$E0F0`）の名称・機能競合の調査記録

状態: **調査と判断記録のみ。実装・スロット配線は行わない。** 名称が未解決のため、`$50` は DEV ROM にも実装しない。
親: [#90](https://github.com/mao2009/oss-pce-cd-bios/issues/90)。台帳: `docs/api-inventory.md` の `$50` 行、`spec/api_contracts.json` の slot 80 レコード。
System Card 互換性、ABI 検証済み、実機・実コア結果のいずれも主張しない。

## 1. 確認できた事実（合意点）

| 項目 | 内容 | 根拠 |
| --- | --- | --- |
| スロット番号 | `$50` = 10 進 80、最後の候補 | 台帳 81 行（`$00..$50`） |
| 候補入口 | `$E0F0`（`$E000 + 3 × $50`） | 台帳の計算式。Stum は表に JSR `$E0F0` を載せる。Zeograd は `$E0F0` と明記せず、ジャンプテーブル規則（×3 + `$E000`）から導かれる |
| 入口の性質 | 候補の計算値であり、実装アドレスの証明ではない | `docs/api-inventory.md` の冒頭注記 |

入口 `$E0F0` の位置は Stum の表と台帳が一致する（Zeograd は規則から導かれるのみ）。対立は名称と機能の 2 点だけである。

## 2. 出典ごとの観測

| 出典 | `$50` の名称 | 機能の記述 | 版の範囲 | 性質 |
| --- | --- | --- | --- | --- |
| Zeograd System Card notes | `MA_CBASIS`（`(zeo)` 表記） | 「値を新しい基数へ変換する」。入力 AL=値、BL=基数。出力 CL=上位桁、DL=下位桁。例: AL=39, BL=16 で CL=2, DL=7 | 「system-card 3.0 について述べる」 | 再構成・一部リバースエンジニアリング由来 |
| Stum 2025 offsets | `$50` の番号では見つからず。`ma_div8u` が JSR `$E0F0` に載る | 8 ビット値 2 つの除算で 8 ビット結果を得る、と要約される（翻訳・引用はしない） | 版別の番地表（1.0 は N/A、2.0 `$FDD1`、2.1 `$FDDB`、3.0 `$FDDB`、TG2.0 `$FDF4`、TG3.0 `$FDF4`） | 名前は作者による非公式ラベル（ページ記載）。番地は本リポジトリでは使わない（後述） |
| Hu-Go `bios.c` selector（HLE） | `#define MA_CBASIS 0x50`。`MA_MUL16S 0x4F` | 機能の記述はなし | 版の記述はなし | HLE モデルの選択子定義。実行可能な入口の証明ではない |

補足:
- Zeograd と Stum は `$E0F0` を別々の名前で指す。ただし Zeograd は入口を明記せず、規則から導かれる。
- Stum では `$E0F0` の `ma_div8u` が 2.0 以降の複数版に現れる。Zeograd は 3.0 のみを述べる。版の範囲は一致しない。
- `MA_DIV8U` は Zeograd にも Hu-Go にも現れない。`MA_CBASIS` は Stum にも現れない。

## 3. 競合の整理

| 論点 | 状態 | 理由 |
| --- | --- | --- |
| 名称: `MA_CBASIS` か `MA_DIV8U` か | **未解決** | 出典ごとに異なる。Stum の名前は非公式ラベルである |
| 機能: 基数変換か 8 ビット除算か | **未解決** | 両者の記述は互いに排他的。どちらも実機または独立した検証資料による裏付けがない |
| 版: 2.0 以降か 3.0 のみか | **未解決** | Stum は 2.0 から、Zeograd は 3.0 のみ |
| 入口 `$E0F0` | 候補として一致（実装の証明ではない） | 両出典と台帳が一致 |
| 引数・戻り値・保存レジスタ・副作用 | **UNKNOWN** | どの出典も検証可能な ABI を与えていない |

`docs/abi-contracts.md` の Hu-Go 表（`$50` = MA_CBASIS、HLE 選択子）は、HLE の選択子定義であることを明記したうえで残す。これは名称の観測であり、機能の裏付けではない。

## 4. 判断

1. **名称は確定しない。** `MA_DIV8U / MA_CBASIS` の併記を維持する。片方を採用して台帳を書き換えない。
2. **機能は確定しない。** 基数変換の記述と 8 ビット除算の記述のどちらも ABI として採用しない。
3. **実装を開始しない。** `src/overrides/` に `slot_50.s` を置かず、`spec/dev_implementations.json` にも `$50` の実装エントリを追加しない。
4. **番地を採用しない。** Stum の番地（`$FDD1`/`$FDDB`/`$FDF4`）は、`docs/cd-reuse-decision-309.md` の 42 行目が示す「非商用条件の扱いを人間判断」（`DO_NOT_USE_UNTIL_LEGAL_REVIEW`）に従い、番地の根拠に使わない。名称の観測のみを記録する。
5. **確定契約のフィクスチャは作らない。** 確定しているのは `$E0F0` という候補入口だけで、それは既に台帳にある。新規のフィクスチャは追加しない。
6. **DEV 台帳は変更しない。** `spec/dev_implementations.json` の slot 80 は既に `NOT_READY`、`implementation: null` である。本文書はこの状態を変えない。

## 5. 未解決の問い（Issue #90 に記録する）

1. 基数変換と 8 ビット除算のどちらが `$E0F0` にあるのか。System Card 3.0 の正規の資料（ROM 本体の読み取り、または独立した検証資料）が必要。
2. `$50` は 2.0 から存在するのか、3.0 のみか。Zeograd の「3.0 について述べる」と Stum の版表が食い違う。
3. Stum の `ma_div8u` 名の出典は何か。作者の「非公式ラベル」の範囲を超える根拠があるのか。
4. Zeograd の基数変換の記述（AL/BL/CL/DL）は、一次資料と一致するのか。例 39→2,7 の再現に独立した実行が要る。
5. Stum の記述は要約ツールを経由して読んだため、引用文の字句は原文と一致する保証がない。原文の再確認が必要。
